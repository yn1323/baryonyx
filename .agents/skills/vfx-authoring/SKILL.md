# VFXの作り方

このスキルは、ガイド「RPG戦闘VFX：専門用語・計算式・Claudeへの指示ガイド」（2026-10-26改訂）を元に、Unityのエフェクトの「単色でのっぺりする」「全部が同じ動きになる」「透ける霧と鋭い光のメリハリが弱い」を直すための進め方を扱う。
ガイドの章は `references/` に分けて置き、これまでの制作で分かったコツを [lessons.md](references/lessons.md) に足した。
エフェクトの出来は、形1つの質よりも、層の分け方、時間の組み立て、周りへの光の影響に左右される。

## 前提

- 今はスマホの負荷より見た目の品質を優先する。最初から粒数・層の数を削って簡略化しない。性能の最適化は、見た目が成り立った後の別の工程にする（[エフェクトの描き方](../../../doc/art/direction.md#エフェクトの描き方)の表現の強さ）。
- **外部の画像素材を使わない。** PNG、画像生成AIの出力、購入素材、写真、外部のFlipbook、既存のノイズ・法線の画像に頼らず、形・濃淡・ノイズ・材質をC#とHLSLで生成する。参考画像は観察用であり、実行時の素材にしない（[エフェクトの描き方](../../../doc/art/direction.md#エフェクトの描き方)）。
- 「画像なし」は外部の画像アセットなしという意味である。コードで生成したTexture2D・Texture3D・RenderTexture、屈折用の画面のキャプチャ、通常のフレームバッファは使ってよい。使うときは生成コード・シード・設定を残し、画像ファイルとして保存しない。召喚獣のような計算で描きにくい物は、例外としてユーザーに相談する。
- キャラがドット絵でも、光・煙・水・氷をピクセル表現に限定しない。滑らかな半透明、反射、背景の歪みを使う。
- オクトパストラベラー系の参考画像は美術上の参考であり、内部のシェーダーや描画手法を示す資料ではない。静止画から時間変化は断定できない。
- 属性や技のレシピは表現の候補集であり、ゲームへの全採用を決めるものではない。式は制作の出発点となる近似で、数値は仮の調整値である。

## 最初に確認すること

作り始める前に、次を実際の設定とコードで確かめる。
記憶や既存の説明文だけで判断しない。

1. **環境**：Unityのバージョン（`client/ProjectSettings/ProjectVersion.txt`）、レンダーパイプライン（`client/Packages/manifest.json`）、レンダラーの種類（Universal Renderer・2D Renderer）、URPアセットのHDRとOpaque Textureを確かめる。設定名や対応機能を推測で断定しない。環境全体の変更が必要なら、理由を示してユーザーに相談する。
2. **描画経路**：エフェクトを置くCanvasのRender Mode、カメラ、カメラのPost Processing、Volumeを確かめる。`Screen Space - Overlay` のCanvasにはBloomが掛からない（[Bloomが掛かる経路](references/lessons.md#bloomが掛かる経路)）。
3. **既存の部品とシェーダー**：同じ画面の既存のエフェクト、共通の演出部品、形を描くシェーダー、共通の関数（ハッシュ、ノイズ、距離関数）、マテリアルを探し、使い回せるものを確かめる。同じ式を別のシェーダーへ書き写さない。
4. **目的と重要度**：そのエフェクトでプレイヤーに何を感じさせ、何を読み取らせるか（だれが、だれに、どの属性で、どれだけ強く）を確かめる。
5. **画面のHD-2Dの要素**：その画面のポストプロセス（Bloom、色調補正、周辺減光、ティルトシフト）、霧、環境の粒、光芒、暗転の部品を確かめ、エフェクトの層がそれらの前後どこに入るかを把握する。

## 進め方

### 1. 現象と体験を書き出す

見た目から作り始めず、その現象が現実なら何から成り、どう動き、何を残すかを書き出す（[現実の現象を書き出してから作る](references/lessons.md#現実の現象を書き出してから作る)）。
好評だった描き方を、現象の違う技へそのまま広げない。
「重い」「鋭い」「温かい」のような感覚の言葉を決め、形・色・タイミングへ置き換える。
技の重要度に合わせて、大きさ・明るさ・長さ・画面効果の格を決め、弱い技と大技を同じ派手さにしない。
作り方に自信がない現象は、作り直す前にWebで作例を調べる。

### 2. 時間と層の表を作り、ユーザーに見せる

時間を **予兆**（Anticipation）、**発動・着弾**（Impact）、**余韻**（Dissipation）に分け、発光・粒子・煙・破片の出現・ピーク・消失をずらす（[F3：立ち上がりと消散](references/formulas.md#f3立ち上がりと消散)）。
主役は本体・発光の芯・ハロー・霧や煙・粒子・背景の歪みなど、役割の違う4つ前後の層に分け、層ごとに合成方式・透け方・太さ・明るさ・時間を変える（[主役を4つ前後の層に分ける](references/lessons.md#主役を4つ前後の層に分ける)）。
すべての層をAdditiveや同じ透明度に統一しない。
現象の書き出し・時間の表・層の表を技の定義文書に書き、ユーザーの確認を受けてから実装する（[計画を3つの表で先に見せる](references/lessons.md#計画を3つの表で先に見せる)）。
曖昧な依頼は、層の数、透け方、秒数、色、明るさに直して確認する。

### 3. 代表技1つで成り立たせる

複数の技を頼まれても、最初は1つの代表技を選ぶ。
斬撃ならコア・ハロー・ウィスプ、炎なら本体・煙・火の粉の構成を成り立たせてから、ほかの技へ広げる。
確かめる順番は、本体の形と軌道、材質、時間構成である。
形が読める前にBloomを強くして覆わない。
最初は単純な式と仮の色でタイミングだけを確かめると、手戻りが少ない。

### 4. 技法を選んで実装する

層ごとに、[recipes.md](references/recipes.md) で属性の層と式の候補を引き、[formulas.md](references/formulas.md) の合成・減衰・ノイズ・Dissolve・軌道の式と、[procedural.md](references/procedural.md) のSDF・fBm・Domain Warping・Curl Noise・Voronoi・密度場・生成メッシュから選ぶ。

- 単調さを、粒数を増やすだけで解決しない。大きな流れと小さな揺らぎ、硬い輪郭と柔らかい輪郭、速い衝撃と遅い余韻を作り分ける。ランダム性は、全体の方向とシルエットを壊さない範囲で使う。
- 一様な拡大と一様なフェードだけで終わらせない。太さ・半径・閾値・ノイズの位置を進み具合で動かし、削れる・散る・流れるように消す。
- ノイズだけで全属性を色替えしない。炎は密度と上昇、水は連続した面と液滴、氷は硬い面と亀裂、斬撃は鋭い帯、回復は滑らかな上昇という、材質と動きの差を保つ。
- `noise`・`fbm`・`SampleSceneColor` などの説明用の関数名をそのまま残さず、使う関数を実装し、値の範囲・座標系・合成方式を明示する。3D密度やCompute Shaderを使うなら、対応環境とリソースの生成・破棄も実装する。
- 強度、幅、外周の減衰、ノイズのスケールと速度、Dissolveの幅、粒の寿命とサイズ、時間カーブを、意味のある名前と初期値でInspectorなどから調整できるようにする。
- 同じ乱数シードで前の版と比べられるようにし、外部素材なしでクリーンな状態から再生成できるようにする。
- uGUIでの値の渡し方、Bloomの経路、実装経路の選び方は [Unityで組むときの注意](references/lessons.md#unityで組むときの注意) に従う。外部プラグインを使うときは、上の表の「外部プラグインの採用条件」に従う。

Claudeに実装を任せるときの共通指示文は [prompts.md](references/prompts.md) にある。

### 5. 画面となじませる

エフェクトを画面に置くだけでなく、周りを照らす光源として扱い、HD-2Dの要素と反応させる（[周りを照らす](references/lessons.md#周りを照らす)、[HD-2Dの画面となじませる](references/lessons.md#hd-2dの画面となじませる)）。

- 床の光だまり、近くのキャラへの色乗せ、ヒットフラッシュ、背景の明暗で、周りに光を落とす。
- 暗転は真っ黒にせず環境の色を残し、光の届く範囲だけ明るさを戻す。
- 色と明るさは、Bloom・色調補正・周辺減光を通った最終の画面で決める。
- 主役はボケない範囲に置き、主形をキャラの奥と手前に分けて標的を挟む。

### 6. コマを並べて確かめる

動いている状態で見ると勢いでごまかされるが、のっぺり感の原因は止めた1コマに現れることが多い。
予兆・ピーク・消散を含むコマを0.1秒おきに撮り、1枚に並べて見比べる（[撮って確かめるコツ](references/lessons.md#撮って確かめるコツ)）。
静止画がよくても、常に同じ速度・同じ密度なら直す。

- 明るい背景・暗い背景・キャラと重なる状況の、ゲーム内のカメラで確かめる。グレースケールでも主役と芯が読めるかを見る。
- 標的、HPバー、弱点、予告が、エフェクトやダメージ数字で隠れていないか。
- 明滅の頻度と面積が、[安全と読みやすさ](#安全と読みやすさ)の基準を超えていないか。
- スキルの演出は、[スキルのデバッグルーム](../../../doc/features/screens/debug-rooms.md#スキルのデバッグルーム)で1枚ずつ再生して撮り、仕上げに戦闘画面のモックでも実際の流れどおりに撮る。
- 撮影画像の保存先は、[client/AGENTS.md](../../../client/AGENTS.md) の「Unityの操作と検証」に従う。
- 前の版と同じ拍のコマを並べ、明るさの平均などの数値を添える。良くなったかの判断はユーザーに委ねる。

### 7. 共通化してから性能を測る

共通のシェーダーや時間カーブを使い回しつつ、属性ごとの材質と動きは個別に調整する。
見た目が成り立った段階で、重なる板の数と面積、1画素あたりのノイズの回数、粒の数を確かめる（[重さ](references/lessons.md#重さ)）。
今の段階では、表現を削る理由にしない。
端末での確認はユーザーに依頼し、重いときは削る前にユーザーと相談する。

### 8. 展示室へ反映して報告する

追加・変更したエフェクトは、ルートの AGENTS.md の[クライアントアセット展示室](../../../AGENTS.md#クライアントアセット展示室)に従って同じ変更で展示室を更新し、一覧に出ることと、プレビューで再生できることを確かめる。
確かめられなかった段階（Editorだけで確認、端末は未確認など）は、未確認として報告に残す。

## 評価するポイント

完成と判断する前に、並べたコマで次を確かめる。
症状ごとの原因と直し方は [計算で描くときのつまずき](references/lessons.md#計算で描くときのつまずき) と [事例](references/lessons.md#事例) にある。

| 見る項目 | 成功の目安 | 問題がある場合の確認先 |
|---|---|---|
| 透明感 | 背景が見え、濃い部分との対比がある | Blend、αマスク、RGBの減衰、重なり数。全体のαを一律に下げていないか |
| メリハリ | 主役は鋭く、周辺は柔らかい | 本体とハローの独立、強度比、幅比。芯だけが白いか |
| 層 | 主役が、透け方と時間の違う4つ前後の層でできている | 1枚の図形で芯・軌跡・にじみを描いていないか |
| 素材感 | 水・煙・氷が色以外でも区別できる | 反射、屈折、形状、ノイズ、法線 |
| 動き | 大きな流れを保ちながら細部が変化する | 周波数、流速、位相、寿命のばらつき |
| 時間構成 | 着弾にピークがあり、余韻へ減衰する | カーブ、開始時刻、寿命、二次動作。使ったときと後から働くときで同じ物を出し直していないか |
| 現象との一致 | 現実にその現象で起きる物だけが出ている | 斬撃や強風に霧を居座らせていないか。昇る・割れる物が太い幕になっていないか |
| 周りへの光 | キャラ・床・背景が照らされ、暗転しても環境の色が残る | 光だまり、色乗せ、暗転の解き方 |
| 前後関係 | 暗い層が光る層の奥にあり、主形がキャラを挟み、地面との接点がある | 描く順番、床に寝かせた層 |
| 可読性 | キャラと命中点を見失わない | 発光面積、重なる位置、画面全体の露出 |
| 背景との整合 | 明暗の背景の両方で形が読める | Additiveの背景依存、αの本体層、露出 |
| 再利用 | 色替え以外にも技を差別化できる | 軌跡、素材、時間、密度、レイヤー構成 |

## 安全と読みやすさ

- 画面全体の閃光や大きな面積の明滅は、[WCAG 2.3.1](https://www.w3.org/WAI/WCAG21/Understanding/three-flashes-or-below-threshold.html)と[Xbox Accessibility Guideline 118](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/118)の基準内に収める。大きな面積の明滅と、彩度の高い赤の明滅は特に避け、高コントラストの縞模様を広く出さない。戦闘の演出で決めた閃光の間隔と濃さは、[スキルの演出と背景](../../../doc/features/screens/battle-effects.md#スキルの演出と背景)に従う。
- 画面揺れ、閃光、ヒットストップは、強さを下げる・止める設定で弱められるようにする。
- 長く感じるエフェクトは長すぎる。連続して使う技ほど短くする。
- 戦闘中に隠してはいけない情報は、[戦闘中の情報の優先順位](../../../doc/features/combat.md#戦闘中の情報の優先順位)に従う。

## 完了報告

完了時は、次をまとめて報告する。
確かめた内容と、確かめていない内容を区別する。

- 作った・直したエフェクトと、狙った体験（感覚の言葉）、書き出した現象
- 時間の表と層の表、各層の役割と合成方式
- 使った式・シェーダー・生成物（生成テクスチャやバッファがあれば生成元と用途）、Unityでの実装経路とその理由
- 調整できるパラメーターと初期値
- 画面のHD-2Dの要素（光、暗転、ポストプロセス、ボケ、霧、カメラ）との組み合わせ方
- 並べたコマと、評価するポイントの結果
- 前の版と同じ拍のコマを並べた比較と、比べた数値。良くなったかの判断はユーザーに委ねる
- 展示室への登録状況
- 未確認の事項（端末での見え方と負荷、ほかの画面比率など）

Webで調べた場合は、公式資料と設計上の推論を分け、対象のUnityバージョンと参照日を添える。
