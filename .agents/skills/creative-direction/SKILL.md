# 見た目と音を一緒に決める

演出・画像・アセット・効果音・BGMを、ユーザーと選びながら作るときの進め方である。
「作ってから見せる」を1回で終わらせず、今の状態を撮る → 課題 → 複数の案 → 選ぶ → 作る → 自分で確かめる → 送る → 直す、を回す。
2026-11-02に、商会と戦闘のスキル覚醒の演出を作り直したときの流れを元にしている。

見た目の案を「提案して」と頼まれたら、文章の案だけで返さず、手順3のとおりCodex CLIの画像生成で作った絵で見せる。
文章は、絵に添える狙い・注意・手間の一言にとどめる。
2026-11-02、商会の買う・売るの演出を文章の表だけで提案し、ユーザーから画像で出し直すよう言われた。

作る技法は担当のスキルに任せ、ここには持たない。

| 対象 | 作る技法 | 案の作り方 |
|---|---|---|
| 演出（エフェクト） | [vfx-authoring](../vfx-authoring/SKILL.md) | 今の画面を土台にCodex CLIで場面の絵を作る |
| ドット絵・画像・アセット | [pixel-art-standards](../pixel-art-standards/SKILL.md) と各生成スキル。ゲームに入れるときは [image-compression](../image-compression/SKILL.md) | Codex CLIで、今の画面に置いた姿の候補を作る |
| 効果音・BGM | [sound-authoring](../sound-authoring/SKILL.md) | フリー素材の候補を、鳴らす場面の動画に重ねる |
| 画面の構成 | [ui-advisor](../ui-advisor/SKILL.md)・[ui-tone-manner](../ui-tone-manner/SKILL.md) | 今の画面を土台に配置の案を作る |

見た目の決まりとユーザーの好みは [アート方針](../../../doc/art/direction.md)（演出は[エフェクトの描き方](../../../doc/art/direction.md#エフェクトの描き方)）、音の決まりは [効果音とBGM](../../../doc/rules/sound.md) を正本とし、案を作る前に読む。

## 1. 今の状態を撮る

指摘を受けた物を、ユーザーが見たのと同じ形で記録する。記憶やコードを読んだだけで判断しない。

- 演出：0.1秒おきのコマを撮って1枚に並べ、気になるコマは元の解像度で切り出して拡大する。撮り方は [vfx-authoring の撮って確かめるコツ](../vfx-authoring/references/lessons.md#撮って確かめるコツ)と [Unity EditorとCLIの知見](../shared/unity-editor-notes.md#撮影)に従う。
- 画像・アセット：実際の画面に置いた状態を撮る。単体の画像だけで判断しない。
- 音：鳴る場面を録画し、今の音を重ねた動画にする（[sound-authoring](../sound-authoring/SKILL.md)）。
- 同じ物を使う場所をすべて探す（呼び出し元・共通の部品・Prefab）。1か所を直すとほかの画面も変わるかを、この時点で把握する。

## 2. 課題を言葉にする

撮った物から、何がなぜ悪いかを、時刻か場所と一緒に短く書き出す。

- 例：「1.2〜2.7秒：選ぶ間、覚醒前のカードが小さな丸になり、何が覚醒するか読めない」「2.9〜3.5秒：山場が画面の上端で切れる」。
- 主役が読めるか、山場が見えるか、終わり方、色、ほかの画面との食い違いを見る。
- 見た目の好みと、演出が起きる理由（現象）を分けて書く。

## 3. 今の画面を土台に案を作る

- 案は、今のゲーム画面の撮影と実際のアセット（カードの絵・キャラ・UI）をCodex CLIの画像生成（[codex_image.py](../shared/scripts/codex_image.py)）に添付して作る。何もない所から描かせない。絵は完成した一瞬の見本であり、ゲームの素材にはしない。
- まず1案を数コマで見せ、ユーザーが「何パターンか」と言ったら、方向性の違う案を5つ前後作る。色や大きさだけの違いにせず、見せ方の考え方を変える（例：割れる・裏返る・ほどける・組み直る・星座）。
- 1案ごとに、流れが分かるコマ（溜める・山場・見せる）と、同じ物を使うほかの画面のコマ（例：商会に加えて戦闘）を作り、1枚の画像にまとめて送る。
- 案ごとに一言添える：狙い、既存の演出や画面と似てしまう点、作るときの手間。
- 依頼文は案と場面ごとにファイルへ書き、作り直せるよう出力と一緒に残す。共通の条件（画面を変えない、文字を足さない、外部素材を使わない描き方）は全案で同じ文にする。
- 生成は並べて走らせ（5〜6本ずつ）、終わるまでの間に影響範囲を調べる。

## 4. 選んでもらう

- 選んだ案と、選ばなかった案との違いを記録する。以前に決めた方針（文書の決定の記録）と比べ、続きか方針転換かを書く。
- 組み合わせ（「Aの溜めとBの割れ方」）も受ける。
- 影響範囲（手順1で調べた場所）をユーザーに伝え、全部そろえるか、一部だけにするかを確かめる。

## 5. 作る

担当のスキルに従って作る。このスキルから加える注意は次のとおり。

- 選んだ絵の印象（主役の位置と大きさ、色、何が画面を占めるか）を先に合わせ、細部はあとで詰める。
- 使う場所ごとに違う所（配置、表示時間、背景）は、共通の部品の設定で分け、部品を複製しない。
- 色などをスキルやアセットごとに手で決める表は、絵と食い違いやすい。絵から取れるなら取り、取れないときの決まった値を持たせる。

## 6. 自分で確かめてから送る

- 送る前に、自分で動画をコマに分けて見る。指摘のあった瞬間は拡大し、前の版と同じ場面を並べて比べる。
- 原因が分からないときは推測で直さず、試して確かめる（例：画面の写し取りがどの時点の画面か、上下の向き）。
- 録画は [unity-video-recording](../unity-video-recording/SKILL.md) に従う。Editorが背面で遅いときの撮り方は [Unity EditorとCLIの知見](../shared/unity-editor-notes.md#撮影)にある。
- シェーダーを変えた直後は仮の色で描かれる。一度再生してから撮る。
- Play中や撮影で、シーン・Prefab・設定に入った変更は、元に戻してから終える（開いているシーンは別のシーンを開いてから戻す）。
- 並行して作業しているチャットがあるときは、Editorの札を取り、同じファイルを編集していないかを差分で確かめる。ほかのチャットの差分が入ったPrefabは作り直さない。

## 7. 送って、指摘を1つずつ直す

- 動画や画像は、場面・解像度・長さ・何を直したかを一言添えて送る。割れる瞬間のような短い山場は、スローも添える。
- 指摘は1つずつ直し、直すたびに撮り直して送る。「あまり変わらない」と言われたら、変化が見える形（前後の並べ、拡大）で見せ直す。
- 指摘が2通り以上に取れるとき（例：「中央から始まる」が場所なのか割れ方なのか）は、作り直す前に選択肢を出して確かめる。両方と言われて試した結果が悪ければ、動画を見せて選び直してもらう。
- 「なくてもいい」と言われた物は、まず外す案を作って見せる。
- 好み・不評と、その理由になった指摘は、同じ変更で文書の決定に書き足す（見た目は [アート方針](../../../doc/art/direction.md)、演出の仕様は各機能の文書、音は [効果音とBGM](../../../doc/rules/sound.md)）。

## 完了報告

- 選んだ案と、直した指摘ごとの対応
- 同じ物を使うほかの画面への影響と、そろえたかどうか
- 送った動画・画像と、撮り方の注意（コマ数が少ない、速さは実際どおり、など）
- 実行したテストの結果、戻した変更（シーン・設定）
- 確かめていないこと（端末での見え方と重さ、ほかの色や画面比率）
