# UIの検証と保守

## 変更前のレビュー

次の項目を設計メモに記録する。

- 対象画面、入口、出口、戻る先、主要CTA、キャンセル。
- 状態図（通常、ロード、空、無効、実行中、成功、失敗、再試行）。
- データ所有者、保存境界、通信境界、報酬の冪等キー。
- タッチ、マウス、キーボード、ゲームパッド、OS戻るの入力対応。
- Safe Area、縦横、基準解像度、最小タッチ領域、文字の最大長。
- ローカライズキー、複数形、単位、日時、フォントフォールバック。
- Pixel Artのグリッド、フィルター、Atlas、9-slice、圧縮、音・触覚・モーション。
- 画面表示、操作成功、離脱、エラー、報酬受取の計測目的。
- Edit Mode、Play Mode、実機・手動で確認するケース。

この表が空欄のまま見た目から実装しない。仕様が未確定なら、未確定のまま仮定を明示し、仮定をコードや報酬データへ埋め込まない。

## 実装後の機能確認

### 状態・遷移

- 同じ画面を開閉してもイベント購読、Tween、Coroutine、Addressables参照が増えない。
- OSの戻る、画面外タップ、キャンセル、二重タップ、連打、ローディング中の入力が定義どおりになる。
- アプリ中断・復帰、シーン再読込、端末回転、通信再試行後も表示と保存状態が一致する。
- 付与済み、表示済み、受取済み、失敗、期限切れを区別できる。

### レイアウト・アクセシビリティ

- ノッチ、ホームジェスチャー、ステータスバー、ナビゲーションバーにCTAや重要数値が重ならない。
- 最小・最大アスペクト比、低解像度、高DPI、タブレット、折りたたみ、画面回転で操作不能にならない。
- ボタンのヒット領域、隣接間隔、押下・フォーカス・無効状態が見える。
- 色だけでなく文字・形・アイコン・音・触覚の代替がある。
- 文字サイズを増やした場合、数字の桁が増えた場合、翻訳が伸びた場合に重要な操作が隠れない。
- モーション低減、音量0、振動無効でも結果とエラーが分かる。

### 性能・資産

- 画面の初回表示、再表示、スクロール、報酬演出、画面遷移のフレーム時間を目標端末で測る。
- uGUIのCanvas再構築、Layout再計算、再利用セル、透明オーバードロー、Atlas分割、フォントアトラスを確認する。UI Toolkitを例外採用した画面では、仮想化と動的アトラスも確認する。
- 画面を閉じた後にテクスチャ、Prefab、Render Texture、購読、Tween、非同期処理が残らない。
- Addressablesの失敗、解放、キャッシュ、言語切り替え後の参照を確認する。
- ドット絵のFilter、MipMap、圧縮、PPU、Pivot、Sprite Atlasの設定が基準から外れていない。

## テストの具体例

Edit Modeでは、報酬集計、在庫上限、日付境界、確率表の合計、比較表示、戦闘コマンドの有効条件、状態遷移、ローカライズキーの存在を固定データで検証する。

Play Modeでは、次のシナリオを一つのテストまたは手動チェックとして残す。

1. 起動してホームを表示する。
2. クエストを選び、コマンド戦闘で対象を選択する。
3. コスト不足、無効対象、キャンセル、決定、勝利、敗北を通る。
4. 結果画面で報酬を受け取り、インベントリ・強化画面へ進む。
5. 受取中に画面を閉じる、アプリを中断する、通信を失敗させる。
6. 復帰して、報酬が二重付与されず、未受取または成功状態を正しく表示する。

スクリーンショット比較を使う場合、ランダム演出、時刻、フォントのアンチエイリアス、通信結果を固定し、差分を「許容」「要確認」「不具合」に分類する。画像差分だけで入力可能性や報酬の正しさを保証しない。

## 保守ルール

- 共通コンポーネントの変更は、使用画面、状態、入力、ローカライズ、テーマ、スクリーンショットを列挙してから行う。
- 画面固有の例外を共通部品へ追加する前に、別コンポーネントまたは拡張スロットで表現できるか検討する。
- UIキー、報酬ID、計測イベント名、アセットアドレスを勝手に再利用しない。削除や改名は、保存・通信・分析の参照を検索してから行う。
- Unityやパッケージを更新するときは、UIシステム比較、Input System、Localization、Addressables、Test Frameworkの該当バージョンを確認し、画面の見た目だけでなく入力・ロード・フォーカスを再検証する。
- テーマ変数、フォント、アイコン、効果音、振動、モーション設定を一か所で確認できるようにする。画面ごとの直書きカラーやタイミングを増やさない。
- 古い画面を修正する場合も、依頼外の全面整理を始めない。壊れた挙動と保守上の問題を分け、必要な範囲だけを直す。

## 計測と改善

イベントは、判断を変えるために必要なものだけ送る。画面表示とCTA表示、CTA押下と処理成功、報酬付与と報酬表示、通信失敗と再試行を一つのイベントへ混ぜない。IDや自由入力テキストなどの個人情報を含めず、既存のプライバシー方針へ従う。

UI変更の評価では、D1・D7の継続率だけで良し悪しを決めない。チュートリアル完了、戦闘開始、コマンド誤操作、結果画面到達、報酬受取成功、再試行率、クラッシュ、フレーム時間、ロード時間、問い合わせ内容を合わせて見る。報酬を強くして継続だけを上げると、コアゲームを遊ばず受取だけを目的にする可能性があるため、行動の質も確認する。

既存のRemote Config、実験、Game Overrides、Analyticsがある場合だけ段階的ロールアウトを使う。変更前に対象、終了条件、ロールバック、保存互換性、オフライン時の既定値を決める。外部サービスがないプロジェクトでは、UIのローカル状態とテスト用固定値で再現できる設計を優先する。

## 完了報告の型

作業完了時は、次の順で日本語にまとめる。

1. 変更した画面・状態・データ・アセット。
2. UIシステム、入力、安全領域、ローカライズ、報酬処理の判断。
3. 自動テスト、Unity Editor確認、実機確認、性能確認の結果。
4. OAuth、権限、外部サービス、未接続端末など、コード以外の未確認事項。
5. 次に必要な判断がある場合だけ、具体的な選択肢を一つ提示する。
