# 実務・研究・コミュニティから得たUIのコツ

この資料は、Unity・Apple・Androidの公式仕様に加えて、ゲーム開発者、UX実務者、研究者、コミュニティで共有されている実践知をまとめたものだ。公式仕様・法令・ストア要件は制約として扱い、実務記事やコミュニティのコツは仮説として扱う。後者をそのまま正解にせず、端末、プレイテスト、既存のゲームループで検証する。

## デザインから実装へ渡すときの実務知

### 見た目ではなく振る舞いを渡す

デザインファイルやスクリーンショットだけでは、実装者が状態や入力を推測することになる。各部品・画面について次を一緒に渡す。

- 目的、主操作、二次操作、戻る先、操作できない条件。
- Anchor、Pivot、Stretch、Safe Area、最小・最大幅、親が変わったときの追従方法。
- 通常、押下、フォーカス、無効、ロード、空、エラー、成功、通信再試行の見た目と操作。
- タップ、長押し、スワイプ、ゲームパッド、キーボード、OS戻る、画面外タップの扱い。
- 文字が長くなった場合、数字が桁増加した場合、ボタンが隣接した場合の振る舞い。
- アニメーションの開始条件、時間、スキップ、モーション低減時の代替。

Figmaなどはフロー、ワイヤーフレーム、プロトタイプに使い、uGUIのPrefabと実機で最終的なサイズ・入力・状態を確定する。Figmaの見た目をそのままUnityのレイアウト値へ変換せず、基準解像度とSafe Areaから再計算する。

画面を実装する前に、すべての共通部品を一画面で並べる「UI zoo」またはコンポーネントギャラリーを作ると、状態漏れ、テーマの不統一、翻訳による崩れを早く見つけられる。ゲーム本編のシーンへ依存させず、固定データで状態を切り替えられるようにする。

### HUDは最大の混乱条件で評価する

HUDの初稿を静かなメニューで判断しない。ボス戦、画面揺れ、パーティクル、ダメージ数字、複数の状態異常、タイマーが同時に出る場面で、重要な情報が読めるかを見る。情報を「次の判断に必要」「あると便利」「飾り」に分け、下位のものを隠しても戦闘判断が変わらないなら常時表示しない。

スマホでは親指や手のひらが画面の一部を覆う。実機を持った状態でスクリーンショットを確認し、敵の対象、残り時間、確定ボタン、危険表示を手で隠せない位置へ置く。実務記事やコミュニティでは、実機を少し離して見たときの可読性、TVやSteam Deckでの距離、フォントの小ささが頻繁な失敗として挙げられている。これは対象端末に合わせて試験するための観点であり、固定の文字サイズ規則ではない。

「目立つ」ことと「優先度が高い」ことを同じにしない。低優先度のバッジ、常時点滅、装飾ゲージ、二重の通貨表示が主CTAや戦闘結果より目立つ場合は、色、面積、動きの順に減らす。

## RPG・コマンド戦闘の実装に効くコツ

- コマンドを確定する前に、対象、コスト、予測効果、行動順への影響を同じ視線内で確認できるようにする。
- 無効なボタンを黙って押せなくするだけにせず、「MP不足」「対象外」「沈黙中」など理由を表示する。
- 不可逆な消費、逃走、降参、売却は一回の誤タップで確定させず、確認または短い取消期間を用意する。
- オート、倍速、演出スキップを使っても、対象、消費、結果、状態異常、報酬が飛ばされないようにする。
- 装備比較は、現在値、変更後、差分、条件、消費、取り消し方法を同時に示す。長押しだけへ重要情報を隠さない。
- 同じコマンドが複数キャラクターにある場合は、選択中のキャラクターを色だけでなく名前、枠、位置で示す。
- 戦闘結果は演出が終わるまで閉じ込めず、結果が確定した時点で次へ進める。演出は再生、スキップ、短縮を選べるようにする。

## 報酬・経済・オンボーディングのコツ

報酬は、数字を増やす演出ではなく、行動の意味を理解させる説明である。表示順は「何を達成したか → 何が増えたか → 何に使えるか → 次に何を選べるか」とする。報酬カードには理由、数量、希少度、期限、進行、受取状態、次のCTAを持たせる。

- 付与と表示を分ける。演出中にアプリが落ちても、再入場時に受取状態と在庫が一致する。
- `すべて受け取る` は、部分成功・在庫上限・通信失敗を個別に再試行できるようにする。
- 進行報酬は現在値と必要値、次の一回で得られるもの、期限、途切れた場合の扱いを示す。
- 連続ログインだけを価値の中心にせず、戦闘、探索、運動などコア行動を行った結果として報酬が出る設計を優先する。
- 報酬量・頻度は、プレイヤーの動機、資源の入口（source）、消費先（sink）、成長曲線を表にしてから決める。S字曲線や日次周期は業界の例であり、そのまま採用せず、シナリオ別のシミュレーションと小規模テストで確認する。
- 早期報酬は機能を教える用途へ割り当てる。新しい装備を渡すなら、装備画面、比較、装着後の効果まで一続きで体験させる。
- ランダム報酬は入手前に候補、確率、保証・天井、重複、消費通貨、更新時刻を確認できるようにする。課金を伴う場合はストア・地域要件を優先する。
- 連続日数が切れたときに過度な罰を与えず、救済、休息、後からの受取を設計する。運動や健康データでは、休止・中止・計測失敗を失敗扱いにしない。

オンボーディングは長い説明を先に読ませず、「短い説明 → 安全な操作 → 直後の結果 → 次の選択」の小さいループにする。スキップ、後で見る、ヘルプからの再生を用意し、チュートリアルで使った同じボタン名とアイコンを本編でも使う。初回に通知、評価、課金、複雑な権限を重ねると目的が分散するため、必要な瞬間まで遅らせる。

## 2Dドット絵の現場で起きやすい問題

- ワールドのピクセル密度とUIのピクセル密度を決め、PPU、基準解像度、Filter、圧縮、MipMap、Sprite Atlasを同じ表で管理する。
- Spriteの見た目の大きさとButtonのヒット領域を分ける。小さなドット絵を無理に拡大して押させず、透明な当たり領域と明確な選択枠を使う。
- 基準解像度で描いたUIを非整数倍で拡大しない。端末ごとの余白はSafe Areaとレイアウトで吸収し、絵そのものを引き伸ばして合わせない。
- 輪郭がぼける場合は、書き出し時のリサイズ、圧縮、Filter、Canvasのスケール、カメラのサブピクセル位置を順に確認する。
- 枠やパネルを9-sliceにする場合は、角のピクセルを伸ばさない境界を先に決める。枠の太さが画面幅で変わるなら、画像ではなくレイアウトの問題として直す。
- ドット絵の装飾性を優先して、文字、コントラスト、ヒット領域、状態差を犠牲にしない。重要な状態は形、ラベル、音、触覚の複数チャンネルで伝える。

## 運動・健康に関わる画面のコツ

運動セッションには、開始前、許可待ち、計測中、休憩、一時停止、中止、データ欠落、保存中、完了、再試行を用意する。計測値の取得時刻、単位、推定・実測の区別、権限状態を近くに置き、古い値を現在値のように表示しない。

「目標未達」「連続日数の途切れ」を責める文言や、休むと損をするように見える報酬を避ける。中断や休息も次に戻りやすい選択として扱う。健康データをゲームの勝敗や課金の根拠にする場合は、値の限界と問い合わせ先を仕様で定め、個人情報を計測イベントへ直接送らない。

## アクセシビリティとプレイテストのコツ

Game Accessibility GuidelinesとXbox Accessibility Guidelinesは、コントラスト、文字、字幕、ナレーション、入力、フォーカス、時間制限、モーション、光過敏、破壊的操作などを設計・テストの観点として整理している。必須要件の一覧として丸写しせず、対象OSとゲームの入力経路に対応するチェック項目へ落とす。

プレイテストは「楽しかったか」だけを聞かず、次のように観察する。

1. 画面を5秒だけ見せて、何が起きていて次に何を押すかを言ってもらう。
2. 課題（例: 最も安全なコマンドを選ぶ、未受取報酬を受け取る）を渡し、説明せずに操作してもらう。
3. 迷った場所、誤タップ、戻る操作、読み飛ばした文章、押せない理由を記録する。
4. 完了率、エラー数、完了時間、再試行、主観的な確信度を、端末・解像度・入力方法と一緒に保存する。

初心者と経験者を分け、画面を見ている時間ではなく判断できたかを評価する。数値が改善しても、報酬を受け取るだけでコアゲームを遊ばなくなっていないか、課金や継続を誤タップで押していないかを確認する。

## 保守しやすいUIへ落とす方法

- 画面状態、共通部品、デザイントークン、ローカライズキー、報酬ID、計測イベント、アセットアドレスを一覧化する。
- Prefab Variant、ScriptableObject、テーマ変数を使い、色、間隔、角丸、枠、文字スタイル、演出時間を画面ごとに直書きしない。
- 画面を開くたびにイベント、Tween、Coroutine、Addressables参照が増えないよう、購読・キャンセル・解放を同じ所有者へ置く。
- 表示状態とサーバー・保存状態を分け、画面を閉じても処理中の結果を失わない。報酬の受取は安定したIDで冪等にする。
- 画面状態表とスクリーンショットを変更レビューへ添付し、通常、押下、無効、ロード、空、エラー、翻訳伸長を一つの差分で確認する。
- 実務上のコツを採用したときは、根拠（公式、研究、記事、コミュニティ）、仮説、測定方法、見直し条件をコメントまたは設計メモに残す。
