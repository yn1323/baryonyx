# RPG・運動・ドット絵ゲームのUX設計

## 画面の骨格

初期案は、次の画面をゲームの実装状況に合わせて採用する。

| 画面 | プレイヤーの目的 | 必ず見せる状態 |
| --- | --- | --- |
| 起動・復帰 | 続きから始める | 保存・同期・ロードの状態、再試行、キャンセル |
| ホーム | 今日何をするか決める | 続き、今日の目的、未受取報酬、主要通貨、通知 |
| マップ・クエスト | 次の挑戦を選ぶ | 推奨、解禁条件、消費、難易度、獲得物、戻る先 |
| パーティー・装備 | 編成と強化を決める | 現在値、比較対象、変更差分、条件、消費、確認 |
| コマンド戦闘 | 安全に行動を選ぶ | 行動者、対象、コスト、効果、順番、確定・キャンセル |
| 戦闘結果 | 達成と次の行動を理解する | 勝敗、経験、ドロップ、未受取、再戦、戻る先 |
| インベントリ・ショップ | 持ち物と交換を管理する | 所持数、上限、価格、購入後、期限、確認 |
| 運動セッション | 安全に計測と実行を行う | 開始条件、経過、休憩、一時停止、終了、計測品質 |
| 設定・ヘルプ | 自分に合わせる | 文字、音、振動、モーション、入力、言語、再チュートリアル |

画面を追加するときは、どの目的を満たすか、どの状態を保存するか、途中離脱時にどこへ戻すかを先に決める。ホームにすべてを詰め込まず、通知バッジは未対応の理由がある場合だけ表示する。

## オンボーディング

初回は、操作説明のスライドを読むより、短い安全な操作を自分で実行して結果を得る流れを作る。RPGなら「戦う、勝つ、報酬を使う、次の敵へ進む」の最小ループを、運動なら「許可を説明する、短い計測を始める、停止する、結果を見る」の順で教える。

- 一度に一つの目的だけを出す。
- 先に行動を促し、説明はその操作の近くに置く。
- スキップ、後で見る、ヘルプからの再生を用意する。
- 初回に不要な通知許可、評価、課金、複雑な設定を重ねない。
- チュートリアルで使った同じボタン、色、アイコンを本編でも使う。
- 進捗を失わせるリセットや早送りがある場合は、その結果を明示する。

Appleのゲーム向けオンボーディング指針は、コア・ループを短い段階に分け、プレイヤーが自分で試し、必要ならスキップ・再確認できる設計を勧めている。採用時は本プロジェクトの対象OSと年齢層に合わせて調整する。

## コマンド戦闘

コマンド選択は、プレイヤーが「何を選んだか」「誰に効くか」「何を失うか」「いつ結果が出るか」を判断できる順番にする。

1. 行動者と残り行動可能時間を示す。
2. 攻撃、技能、防御、道具、逃走などの主カテゴリを選ぶ。
3. 対象候補と、対象ごとの有効・無効・危険状態を示す。
4. コスト、威力、状態変化、行動順への影響を確認できるようにする。
5. 不可逆な消費は長押し、確認、または短い取消期間を使う。
6. 実行中はボタン連打を受け付けず、結果と次の行動者を明確にする。

予測値は「予測」「確率」「範囲」などの語で確定値と区別する。攻撃対象が変更された、敵が無効化した、コスト不足、状態異常で使えない場合は、押せないだけで終わらせず理由を近くに表示する。オートや倍速は戦闘の状態を飛ばすため、いつでも解除でき、重要な結果だけを確認できるようにする。

## 報酬の構造

報酬カードや結果画面は、次のデータを別々に持つ。

| データ | 例 | UIでの意味 |
| --- | --- | --- |
| awardId | クエスト達成ID | 二重付与を防ぐ識別子 |
| source | 勝利、運動達成、ログイン | なぜ得たか |
| itemId / quantity | 回復薬3個 | 何がいくつ増えたか |
| rarity | 通常、希少、伝説 | 見た目と説明の差 |
| progress | 7 / 10 | 次の達成まで |
| expiresAt | イベント終了時刻 | 期限と救済 |
| claimState | pending、claimed、failed | 受取と表示を分離 |
| nextAction | 装備、強化、再戦 | 次に選べる行動 |

画面では「達成した事実」「増えたもの」「使い道」「次の一歩」を一つずつ示す。複数報酬はまとめて読めるようにし、アニメーションが終わるまで操作を閉じ込めない。`すべて受け取る` は、部分失敗が起きたときに成功と失敗を個別に再試行できるようにする。

連続ログイン、日次・週次、シーズン、実績、運動目標は、報酬の大きさだけでなく、目標の見通し、達成方法、途切れたときの扱いを表示する。運動や健康のデータを扱う場合は、休息・中止・計測失敗を罰にしない。プレイヤーの安全や身体状況を推測して断定する文言を使わない。

ランダム報酬を有料販売する場合、プラットフォーム要件に従って入手前に確率を表示し、保証、重複、通貨、期限、返金・復元の扱いを明示する。確率を隠したり、受取ボタンと購入ボタンを同じ位置に置いたりしない。

## ドット絵と演出

Pixel Artは、情報の優先順位をパレットと形へ落とし込む。

- 通常、選択、決定、危険、無効、成功、未確認に専用のコントラストを用意する。
- アニメーションは状態変化の原因と結果をつなぐ。報酬なら獲得、収納、使用可能の三段階を長く引き延ばさない。
- 点滅、画面揺れ、強いズーム、連続パーティクルは、設定で弱めるか止められるようにする。
- 効果音、触覚、色、数字のどれかが欠けても、重要な状態が分かるようにする。
- 低解像度のアイコンを拡大して読ませず、拡大詳細やラベルを用意する。

## アクセシビリティと入力

Androidはインタラクティブ要素のタッチ領域を少なくとも48dp、Appleは頻用ボタン44ptを目安にしている。Unityでは見た目のSpriteを小さく保ちつつ、ButtonやRaycastの当たり判定へ余白を設ける。重要な情報は色だけで伝えず、アイコン・形・文字・音声・触覚の組み合わせを使う。

設定へ、文字サイズ、コントラスト、色覚補助、モーション低減、音量、振動、オート・手動、左手向け配置、入力方法、字幕、再チュートリアルを置く。ゲームパッドやキーボードを対象に含める場合は、フォーカス枠とキー表示をタッチ画面の代替として設計する。
