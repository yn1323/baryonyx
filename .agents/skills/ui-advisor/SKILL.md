# スマホゲームUIの設計と実装

このスキルは、画面を見た目だけ整える作業ではなく、プレイヤーが「今どこにいて、何を選べて、選択後に何が変わったか」を迷わず理解できるUIを、Unityプロジェクトで変更しやすく保つために使う。

対象は、ゲーム内HUD、ホーム、パーティー・装備、行き先の選択（分岐ルート）、カードバトル、戦闘結果・報酬、インベントリ・ショップ、歩数の連携と同期、オンボーディング、設定・アクセシビリティ、画面遷移、入力、演出、ローカライズ、UIアセット、性能、テスト、運用改善である。
ゲームの今の企画（戦闘の形式、運動データの範囲、課金の方針）は[ゲーム概要](../../../doc/game/overview.md)と各機能の仕様で確かめ、このスキルの一般論より優先する。

## 発動したら最初に確認すること

1. Unityの実バージョン、対象OS、画面方向、最小・最大アスペクト比、既存のUIシステム（UI Toolkit、uGUI、混在）、Input System、Localization、Addressables、テスト構成を調べる。
2. ルートと対象ディレクトリの `AGENTS.md`、既存の画面遷移・デザイン規約・命名規則・保存方針を読む。
3. 既存の動作を壊さない範囲を定め、既存画面を別システムへ一括移行しない。新規画面だけで済むなら移行を提案しない。
4. 画面の目的、主要なプレイヤー行動、成功・失敗・キャンセル、通信や保存の失敗、再入場時の状態を短く書き出す。
5. 実装前に、画面フロー、状態、データの所有者、入力経路、表示可能な報酬、計測イベント、検証端末を明記する。

プロジェクト固有のUI構成、画面方向、基準解像度、Safe Area、フォント、タップ領域、機種差の確認条件は、[UI設計ルール](../../../doc/rules/ui-design.md)を正本とする。
画面の部品やコードの置き場所と、複数の画面で共有する部品の扱いは[クライアントの構成と依存関係](../../../doc/rules/frontend-design.md#配置を増やすときの基準)に従う。
このスキルには、それらの規則や値を写さない（[docとスキルの使い分け](../../../doc/rules/documentation-policy.md#docとスキルの使い分け)）。

バージョン固有のAPIや推奨は記憶で断定せず、Unity公式マニュアルの対象バージョンを確認する。調査の入口は [references/research-sources.md](references/research-sources.md) にある。

## 作業の進め方

### 1. 画面をプレイヤーの仕事から分解する

画面名の一覧から始めず、ゲームのループを次のように分解する。

- **始める**：起動、ロード、初回説明、復帰、通知された目的の確認。
- **選ぶ**：行き先、パーティー、装備、スキル、手札のカード、対象。
- **実行する**：部屋の移動、カードバトル、報酬受取、交換、購入、歩数の同期。
- **理解する**：HP・エネルギー・状態異常、進行、達成条件、次に得られるもの。
- **戻る**：中断、再開、リトライ、敗北、通信失敗、未受取報酬、設定変更。

各画面について、目的、入口、出口、主要CTA、二次操作、禁止・無効状態、空状態、ローディング、エラー、成功フィードバックを記述する。画面遷移図と状態遷移図を分け、同じ画面でも「閲覧中」「選択中」「確認中」「実行中」「結果表示中」を別状態として扱う。

### 2. UIシステムを用途で選ぶ

採用方針と既存構成は[UI設計ルール](../../../doc/rules/ui-design.md#現行のui構成)に従う。
新しい例外を設けるときは、画面ごとに採用理由、入力イベント、描画順、フォーカス、ライフサイクル、テスト対象を設計メモへ残す。
実装上の責務分担とAPIの判断表は [references/unity-ui.md](references/unity-ui.md) を読む。

### 3. 状態とデータをUIから分離する

UIは表示と入力の変換を担当し、報酬計算、戦闘解決、歩数の記録、在庫更新、保存、通信を直接所有しない。

- 画面ごとに `View`（採用したUIシステムの表示部品）、`Presenter`またはViewModel（表示用の状態と入力変換）、`Service`またはドメイン（ルール・副作用）を分ける。
- 状態は一方向に流し、イベントを受けて表示を更新する。毎フレーム全ラベルを書き換えず、変更された値だけを更新する。
- 画面を閉じても残るデータと一時的な表示状態を分離する。報酬の「付与済み」と「表示済み」「受取ボタンを押した」は同じフラグにしない。
- 画面を再表示しても二重購読、二重付与、二重アニメーションが起きないよう、購読解除・キャンセル・再入場を設計する。
- 報酬・購入・持ち物の増減を保存する処理の置き場所と、再送で二重に処理しないための要求IDは、[data-storage](../data-storage/SKILL.md) と[保存先の決め方](../../../doc/rules/data-storage.md)に従う。UIは、保存中・失敗・再試行を画面状態として表示する。

### 4. 触れる前提でレイアウトする

安全領域、端末の切り欠き、ジェスチャー領域、片手操作、長いテキスト、端末回転、タブレットや折りたたみを想定する。

- Unityの `Screen.safeArea` を基準に、重要な操作と情報を安全領域内へ置く。UI Toolkitでは座標原点が異なるため変換を確認する。
- 端末の論理ピクセルと実ピクセルを混同せず、プロジェクトの基準解像度、Canvas ScalerまたはPanel Settings、スケール係数を決めてから配置する。
- タップ領域の大きさと間隔は[UI設計ルール](../../../doc/rules/ui-design.md)に従い、ドット絵の見た目の小ささとヒット領域を分ける。隣接ボタンの誤タップ、端の戻る・ホームジェスチャーとの衝突を検証する。
- 主操作は親指が届く領域、二次操作は上部やメニューへ置き、戦闘中の重要なボタンを画面端や敵・エフェクトの下へ隠さない。
- 色だけで状態を伝えず、アイコン、形、ラベル、ゲージ、音、触覚、アニメーションの少なくとも二つを組み合わせる。色覚特性、低コントラスト、文字サイズ変更、モーション低減、音なしでも理解できる代替を用意する。
- テキストは翻訳で伸びる前提にし、固定幅で切り捨てない。Smart Strings、複数形、数値・日時・単位、フォントフォールバック、疑似ローカライズを早期に確認する。

#### このプロジェクトの横画面

横画面の設計座標、背景の覆い方、Safe Area配下への配置、確認する画面比率は、[UI設計ルールの画面方向と拡縮](../../../doc/rules/ui-design.md#画面方向と拡縮)と[機種差を確認する条件](../../../doc/rules/ui-design.md#機種差を確認する条件)に従う。
背景の歪み、Safe Area外の操作部品、文字の欠落、タップ領域の不足は、条件ごとに分けて記録する。

### 5. 2Dドット絵のルールをUIにも通す

ピクセルアートでは、ゲームワールドとUIの基準グリッド、整数スケール、Nearest Filter、圧縮、Sprite Atlas、9-sliceの境界をデザイン仕様にする。

- 基準解像度と整数倍で表示できる端末を定義し、非整数スケールやサブピクセル移動で輪郭がぼけないようにする。
- フォント、アイコン、枠、ゲージ、カーソル、ダメージ数字のピクセル密度とアウトライン幅をそろえる。拡大しても読める最小サイズを実機で確かめる。
- 背景と前景、選択枠、危険表示、報酬の希少度を、パレット・形・アニメーションで区別する。点滅や揺れは短くし、設定で弱められるようにする。
- Sprite AtlasやUI Toolkitの動的アトラスは、同時に表示する資産をまとめ、巨大な一枚化や異なる圧縮設定の混在を避ける。フレームデバッガーとプロファイラーで確認する。

### 6. RPG・歩数連動・カードバトルの画面を設計する

詳細は [references/game-ux.md](references/game-ux.md) を読む。実装時は次の原則を守る。

- ホームには「今日の目的」「続きから」「未受取報酬」を優先し、通貨や告知で主要CTAを埋めない。
- パーティー・装備は、現在値、比較対象、変更後の差分、装備条件、消費、元に戻す方法を同じ視線内に置く。長押しだけに情報を隠さず、詳細画面を用意する。
- カードバトルは、手札、使うカードのコストと残りのエネルギー、敵の対象、効果、行動順、キャンセル、確定、実行中、結果を可視化する。タップ一回で不可逆な消費や降参を確定させず、確認または取り消し時間を設ける。戦闘中に隠してはいけない情報は[戦闘中の情報の優先順位](../../../doc/features/combat.md#戦闘中の情報の優先順位)に従う。
- 予測ダメージや命中率など不確実な値は、確定値と予測値をラベルで区別する。状態異常、バフ、デバフ、クールダウン、ターン順にはアイコンだけでなく説明可能な詳細を持たせる。
- 歩数の連携と同期は、許可の前の説明、許可の状態、同期中・失敗・再試行、取得した時刻、ゲームに反映された量を別に扱う。歩数をゲームの有利不利につなげる表示は、ユーザーが意味と限界を理解でき、歩かない日を責めない表示にする（[ゲーム概要](../../../doc/game/overview.md)の運動の位置づけ）。

### 7. 報酬を「意味のある結果」として表示する

報酬は数字を増やす演出ではなく、プレイヤーが何を達成し、何が変わり、次に何を選べるかを理解するための画面である。

- 付与理由、報酬名、数量、希少度、期限、受取済み状態、使い道、次の目標を表示する。
- まず達成事実を短く返し、その後にアイテムの内訳、比較、解禁、次の行動を見せる。`受け取る`、`すべて受け取る`、`後で見る`、`閉じる`を区別する。
- 進行報酬は現在値と必要値を併記し、残りの一回・一歩・一勝など、次の行動へつながる単位で表す。毎日報酬や連続日数は、途切れた場合の扱いと救済を先に説明する。
- ランダム報酬は、入手前に候補、確率、保証・天井、重複時の扱い、消費する通貨、リセット時刻を確認できるようにする。有料のランダムアイテムはプラットフォームの開示要件を満たす。
- 報酬の量や頻度を増やして解決しない。コアゲームの理解、努力の手応え、選択の幅、コレクション、見た目の変化のどれを報いるかを決め、過剰なポップアップ、誤タップを誘う配置、期限を隠す表示を避ける。
- 受取失敗、通信切断、在庫上限、重複、期限切れ、受取済み、アプリ終了途中を画面状態として実装する。演出より先に確定状態を更新し、再入場時に結果が一致することをテストする。

### 8. 実装・検証・保守を同じ変更に含める

画面を追加したら、表示だけでなく状態、入力、データ、アセット、ローカライズ、テスト、計測、保守資料を同時に更新する。実務記事・研究・コミュニティのコツは、根拠の種類と前提を明記し、公式要件と混同せず、端末・プレイテストで仮説を検証する。具体例は [references/community-practice.md](references/community-practice.md) にある。

- 既定のPrefab構造、クラス名、Canvas階層、テーマ変数、画面キー、ローカライズキー、アイコン・音・アニメーションの所有箇所を記録する。UI Toolkitを例外採用した画面だけUXML/USSも記録する。
- 共通ボタン、ダイアログ、タブ、リストセル、ゲージ、報酬カードは状態（通常、押下、フォーカス、無効、ロード、空、エラー）を持つ再利用部品にする。画面固有の例外は共有部品へ逆流させない。
- 操作を求めない通知（「〇〇しました」「準備中」など）は、画面ごとにトーストを作らず、共通の通知の帯で出す。見た目・位置・表示時間とダイアログとの使い分けは[操作を求めない通知](../../../doc/rules/ui-design.md#操作を求めない通知)に従う。
- 画面を足すときは、先に既存の共有部品を探して使う。別の画面にある部品が必要になったら、コピーせずに共有部品へ移してから両方で使う。移す先と移し方は[配置を増やすときの基準](../../../doc/rules/frontend-design.md#配置を増やすときの基準)に従う。
- 画面のPrefabとシーンをコードで生成する場合は、共通の組み立て部品を使い、生成スクリプトごとに配置・画像・ボタン・文字の補助メソッドを書かない。生成スクリプトを直したら、作り直した結果が変わっていないことを[生成スクリプトのリファクタの検証](../unity-csharp-differences/references/refactoring.md)の手順で確かめる。
- 長いリストはuGUIの再利用セルや、例外的にUI Toolkitを採用した画面の`ListView`仮想化を使い、全要素のインスタンス化と毎フレームの全件更新を避ける。頻繁に変わる要素はレイアウト再計算を起こしにくいプロパティ・Transform・テクスチャを選び、プロファイラーで端末上のフレーム時間とメモリを見る。
- Edit Modeで純粋な変換・計算・状態遷移、Play Modeで入力・画面遷移・再入場・報酬受取・ローカライズ・画面回転を検証する。可能ならスクリーンショット比較やテスト用の固定乱数で、見た目と報酬内容を再現可能にする。Play Modeのテストは[シーンテストを軽く保つ](../../../doc/rules/client-testing.md#シーンテストを軽く保つ)に従い、画面の流れを1回ずつ通しつつ、同じ待ち時間を繰り返さない。
- 最低限、縦横、ノッチ・ジェスチャー、低解像度、高DPI、長文、数字の桁増加、色覚・低コントラスト、音なし、モーション低減、タップ連打、戻る、アプリ中断・復帰、通信遅延・失敗、メモリ警告を確認する。
- 計測イベントは目的を一つに絞り、画面表示、CTA表示、操作成功、離脱、エラー、報酬受取、再試行を区別する。個人情報をイベントへ入れず、既存のAnalyticsや実験基盤がある場合だけ接続する。

## 実装時の出力

依頼が設計・実装・レビューのどれでも、作業の冒頭で次を短く提示する。

1. 画面の目的と主要フロー。
2. UIシステムの選定と既存構成との境界。
3. 状態、データ所有者、入力、失敗・再入場の扱い。
4. 主要コンポーネント、アセット、ローカライズ、報酬表示の構成。
5. 実装するテストと、端末・権限・外部サービスのために残る未確認事項。

レビューでは、見た目の好みよりも、誤操作、状態の不整合、情報の欠落、入力不能、安全領域、ローカライズ崩れ、再現できない演出、性能劣化、報酬の二重付与を優先して指摘する。実装や検証を行った場合は、変更ファイル、検証結果、未確認の端末・権限・サービスを日本語で報告する。
