# Unityコードのリファクタ

動作を変えずに、重複したロジックやファイルをまとめるときの進め方。
共通化した部品の置き場所と、共有するかどうかの基準は、このリポジトリの[配置を増やすときの基準](../../../../doc/rules/frontend-design.md#配置を増やすときの基準)を正本とする。
PlayModeテストの書き方は[シーンテストを軽く保つ](../../../../doc/rules/client-testing.md#シーンテストを軽く保つ)に従う。

## 1. 重複を見つける

- 機能をまたいで同じ名前のメソッドを並べ、実装を読み比べる。名前が同じでも、値・順番・引数の違いがある。

```bash
cd client/Assets/Baryonyx
grep -rnE "(private|internal|public) static [A-Za-z<>, \[\]\?]+ [A-Z][A-Za-z]*\(" --include='*.cs' . \
  | awk -F: '{f=$1; sub(/.*\//,"",f); m=$3; sub(/\(.*/,"",m); sub(/.* /,"",m); print m" \t"f}' \
  | sort -u | awk '{c[$1]++; files[$1]=files[$1]" "$2} END {for (k in c) if (c[k]>1) print c[k], k, files[k]}' \
  | sort -rn
```

- Editorの生成スクリプト（Prefab・シーン・画像を作る処理）は、配置・画像・ボタン・文字の補助メソッドが画面ごとに複製されやすい。
- 別の機能のフォルダーにある部品を借りている箇所（`using` で別機能の名前空間を読む、別機能の画像のパスを持つ）も、共通化の対象になる。

## 2. 違いを残して共通化する

- 共通部品は、呼び出し側の多いほうの動作に合わせる。一部の画面だけ違う値は、共通部品の引数にするか、その画面に小さなラッパーを残す（例：案内人の画面のボタンだけ、無効時の色を変える）。
- 生成スクリプトの補助メソッドは `using static` で呼べる静的クラスにまとめると、呼び出し側を書き換えずに済む。
- プレビュー用のシーンやフォントなど、補助メソッドが使う状態は `using` のスコープで開閉し、閉じ忘れと入れ子を防ぐ。
- 画面の切り替え、トーストの表示と消去のように、実行時のコードで同じ手順を繰り返している箇所も、共有部品へまとめる。

## 3. アセットとファイルを移す

- Unityの移動機能（`AssetDatabase.MoveAsset`、Unity CLIの `move_asset`）で移し、`.meta` とGUIDを保つ。
- `AssetDatabase.StartAssetEditing` の中では、同じ一括処理で作ったフォルダーを `IsValidFolder` が見つけられない。`CreateFolder` が「Art 1」のような重複フォルダーを作り、そのフォルダーへの移動は失敗する。移動先のフォルダーを作る処理は、一括処理の外で1件ずつ行う。
- MonoBehaviourのクラス名や名前空間を変えても、Prefab・シーンはスクリプトをGUIDで参照するため壊れない。ただし `m_EditorClassIdentifier` の文字列は古いまま残る。
  - `AssetDatabase.ForceReserializeAssets` で書き直すと、オブジェクトの並び順まで変わって差分が大きくなる。
  - 識別子の文字列だけを新しい名前へ置き換え、再インポートしてから、下の手順で中身が変わっていないことを確かめる。
- テストは、対象のコードの近くへ移し、対応するテスト用アセンブリへの `.asmref` を置く。移したあと、テストの件数が変わっていないことを確かめる。

## 4. 生成スクリプトの結果が変わらないことを確かめる

生成スクリプトはPrefabやシーンを作り直すたびにfileIDを振り直すため、ファイルの差分では比べられない。
[scripts/dump_generated.cs](../scripts/dump_generated.cs) で中身を書き出し、リファクタの前後で比べる。

1. リファクタの前に、生成メニューの処理を実行してPrefab・シーンを作り直し、ダンプを書き出す。コミット済みの状態と比べるため、作り直す前のダンプも取っておく。
2. リファクタ後に同じ処理を実行し、もう一度ダンプを書き出して `diff` で比べる。改名したクラス名以外の差があれば、共通化で値や順番が変わっている。
3. シーンは、Prefabの中の子要素がレイアウトの計算の有無で変わるため、シーン直下の構成だけを比べる（スクリプトの `RootsOnly`）。
4. 比べ終わったら、作り直したPrefab・シーンは `git checkout` でコミット済みの状態へ戻す。中身が同じなら、fileIDだけが変わった大きな差分を残さない。
5. 生成した画像（PNGと `.meta`）は内容が決まるため、移動前のファイルとバイト単位で同じかを確かめる。

生成処理は、開いているシーンを作り直さない。
無題のシーンが開いていると、追加のシーンを作れずに失敗するため、保存済みの別のシーンを開いてから実行する。
接続中のEditorで時間のかかる処理を `eval` すると、CLI側は5秒で打ち切られるが、Editorでは処理が続く。
`editor_status` が `ready` に戻るのを待ち、結果はファイルへ書き出して確かめる。

## 5. 検証と文書

- Unityの再コンパイル（`recompile_status`）、CSharpierの整形と検査、EditModeの全件、関連するPlayModeのテストを実行する。
- PlayModeテストを直した場合は、変更前と後の件数と所要時間を記録し、流れを1回ずつ通せていることを確かめる。
- 移したファイルへのリンクは[文書検査](../../../../doc/tools/README.md)で見つかる。構成の正本（[クライアントの構成と依存関係](../../../../doc/rules/frontend-design.md)）と、移したアセットを載せた文書を同じ変更で直す。
- 移したアセットの展示室の登録は、カタログの自動更新で新しいパスと名前に変わる。差分がパスと名前だけであることを確かめる。
