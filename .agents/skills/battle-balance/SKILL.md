# 戦闘バランスを調べる

戦闘の自動対戦で数字を集め、目安と比べて、原因の場所と直し方の案を出す。
自動対戦の回し方・依頼の項目・本物の戦闘との違いは [戦闘の自動対戦](../../../doc/rules/client-testing.md#戦闘の自動対戦) を正本とし、ここには写さない。
目安のターン数は [戦闘の長さ](../../../doc/features/combat.md#戦闘の長さ)、部屋ごとの倍率と過去の測定は [行き先と敵](../../../doc/features/stage-progression.md#行き先と敵) と [戦闘の試し](../../../doc/features/stage-progression.md#戦闘の試し) にある。

既定では、測って報告するまでを行い、倍率や数値は変えない。
直すのはユーザーが直し方を選んでからにする。
目安が決まっていない数値（たとえば目安のターン数そのもの）は、案として出し、ユーザーに決めてもらう。

## 1. 何を測るか決める

依頼から、次の3つを決めて最初に書き出す。
曖昧なら、いちばん狭い測り方を選んで進め、選んだことを報告に書く。

- **行き先と戦闘**：どの行き先の、魔物・強い魔物・最奥の間・ミミックのどれか、深さ、敵の組み合わせ。ユーザーが特定の戦闘を挙げたら、その組み合わせを `variants` で指定し、全体の傾向も見たいときは全組み合わせも回す。
- **パーティと育ち具合**：初期のまま、推奨Lvちょうど、Lvだけ上げた、カードの品質や覚醒・装備まで育てた、など。「初期のパーティ」は初期装備を付けた状態である（[本物の戦闘との違い](../../../doc/rules/client-testing.md#本物の戦闘との違い)）。装備の有無で結果が大きく変わるため、どちらで測ったかを必ず書く。育てる前提の倍率（[育てる前提の強化](../../../doc/features/stage-progression.md#育てる前提の強化2026-10-24)）を測るなら、初期と育てた後の両方を回して差を見る。
- **戦い方**：1部屋を繰り返す（`single`）か、道を歩いてHPを持ち越す（`through`）か。ユーザーの体感が「冒険の途中でつらい」なら `through` も回す。

## 2. 自動対戦を回す

[回し方](../../../doc/rules/client-testing.md#回し方)に従い、依頼のJSONを置いて `BattleBalanceTests` を実行する。
Editorの札の取り方と返し方は [複数のチャットで1台のEditorを使うとき](../../../doc/rules/client-testing.md#複数のチャットで1台のeditorを使うとき) に従う。

- 最初に1組だけ少ない回数で回し、結果の表が出ることを確かめてから、全組み合わせや多い回数を回す。
- 1回の依頼は札の上限に収まる量にする（目安は正本の文書にある）。多いときは組み合わせや回数を分け、札を取り直して続ける。
- ばらつきを見るため、1組あたり3回以上、結論に使う数字は全体で30戦以上を目安にする。勝率の差を言うときは回数も添える。
- 不自然な結果（1ターン目の与ダメが0、`Timeout` の戦闘、全滅が続く）が出たら、`verbose` で1戦だけ回し、1手ずつの記録を読んで、台本の不具合か戦闘の仕様かを切り分ける。
- 戦闘の計算に関わるファイルを他のセッションが編集中なら、その変更が入った状態で測っていることを報告に書く。

## 3. 目安と比べる

`result.md` の組ごとの表と全体の行を、[戦闘の長さ](../../../doc/features/combat.md#戦闘の長さ)の目安と比べる。
見るのは次の4つである。

- ターン数の平均と幅（分布）。平均が目安どおりでも、幅が広ければ組み合わせ次第で長すぎる戦闘がある。
- 勝率と、倒れた味方の数、勝ったときのHP。ターン数が目安どおりでも、毎回2人倒れるなら「危なすぎる」別の問題である。
- 組み合わせごとの差。どの敵と組むと長い・危ないかを、表の組の欄の敵の名前で特定する。
- 自動対戦と人のずれ。自動のカードの選び方は人と違う（[本物の戦闘との違い](../../../doc/rules/client-testing.md#本物の戦闘との違い)）。ユーザーの体感と食い違うときは、どちらの条件が違うかを書く。

## 4. 原因の場所を突き止める

数字がどこで決まっているかを、敵・部屋・計算・味方の順にたどる。
`result.json` の `enemyStats`（戦闘が始まったときの敵のLv・HP・防御・攻撃の倍率・速度）、`partyStats`（装備を含めた味方のステータスと2回発動の確率）、`dealtByTurn`（ターンごとの与ダメ）が手がかりになる。

- **部屋の倍率**：[行き先と敵](../../../doc/features/stage-progression.md#行き先と敵)の表と、その実装（`AdventureCatalog`）の値が一致しているか。深さの倍率が重なる部屋かどうか。
- **敵の定義**：敵のLv100の値（`CombatEnemyStats`）と行動（`CombatEnemyBehaviors`）。速い敵は味方の番より先に動き、1ターン目の前にHPを削る。溜めのある敵は大技の一撃が重い。
- **ダメージの式**：[ダメージと防御](../../../doc/features/combat.md#ダメージと防御)に従う。防御の定数Kは攻撃する側のLvで決まるため、Lvを上げた敵は、硬くなるだけでなく味方の防御も効きにくくする。敵の防御が削る割合は、Kとの比で見積もる。
- **味方の強さ**：Lvとステータス（[レベルとステータス](../../../doc/features/progression.md#レベルとステータス)）、装備（[装備](../../../doc/features/equipment.md)）、カードの割合と品質、デッキの中の攻撃しないカードの数、エネルギーの増え方。1ターンの与ダメの伸び方（`dealtByTurn`）で火力不足かを見る。

二重がけを疑うときは、倍率を掛ける処理を読み、素の値へ戻してから1回だけ掛けているか、同じ倍率を別の処理でもう一度掛けていないかを確かめる。
`enemyStats` のHPと攻撃を、Lv100の値・成長率・部屋の倍率から手で計算した値と突き合わせると、二重がけやLvの基準のずれはすぐ分かる。

## 5. 直し方の案を出す

案は2〜3個に絞り、それぞれに次を付ける。

- 変える場所（ファイルと定数、またはdocの表）と、変える値。
- 数字の見込み。可能なら、案の値で自動対戦を回し直した結果を付ける。回していない見込みは「見込み」と書き、計算の根拠を添える。
- その案で変わる他の戦闘（同じ倍率を使う他の行き先、世界地図の戦闘など）。
- 目安そのものを変える案は、ユーザーが決める事柄として分けて書く。

## 6. 必要なら実際に遊んで確かめる

自動対戦の数字だけで判断しにくいとき（操作の分かりにくさ、演出の長さ、1ターンにかかる時間）は、Editorで実際に遊ぶ。
サーバーが要る流れでは、サーバーを自分で起動せず、何をつなぐ必要があるかをユーザーに伝える。
Playに入ったら、終えたあとに必ず止め、変えた設定と足した物を片付けてから札を返す。

## 7. 報告の形

結論から書き、次の順に並べる。

1. 結論：目安と比べてどうだったかを1〜2文で。
2. 測った条件：行き先・戦闘・パーティ・回数・種・自動対戦と本物の違いのうち効いたもの。
3. 測った数字：`result.md` の表から必要な行。全組み合わせなら、全体の行と目立つ組だけにする。
4. 課題：重い順に。それぞれに数字、原因の場所（ファイルと行）、直し方の案と見込み。
5. 未確認のこと：回していない条件、人の遊び方とのずれ、他のセッションの変更の影響。

測った結果を残すときは、[戦闘の試し](../../../doc/features/stage-progression.md#戦闘の試し)に日付つきの小節で追記する。
