# 変更をコミットする

現在の変更を調べ、今回の依頼に属するものだけを論理単位でコミットする。
ユーザーや並行作業者の変更は残し、ステージしない。
このスキルは、ユーザーが `$commit` を明示した場合だけ使う。

## 検証の再利用

最後の関連変更より後に同じ作業ツリーで成功した検証は再利用し、コミットのためだけに再実行しない。

## ワークフロー

### 1. 対象範囲と検証を確認する

- チャットの依頼と `git status` を照合し、今回の変更を特定する。
- 対象範囲の `AGENTS.md` に従って必要な検証を実行する。
- 検証のために依頼外のコードを変更しない。失敗時は原因を報告し、未検証のままコミットしない。

### 2. 変更の収集

```bash
git status          # -uallは使わない
git diff            # unstaged
git diff --cached   # staged
```

変更なしなら「コミットする変更がありません」と報告して終了。

### 3. 除外ファイルを残す

- `.env*` / credentials / secrets系
- Unityの `Library/`、`Temp/`、`Logs/` などの生成物、ビルド成果物。追跡対象の `.meta` は対応するアセットと一緒に含める

これらが変更に含まれても内容を変更または復元しない。
依頼外のファイルがステージ済みでも、indexの状態を変更しない。
今回のコミットから安全に除外できない場合は、対象と理由を報告して停止する。

### 4. 論理グループへの分割

**同一グループにすべきもの:**
- `server/` のDB定義・マイグレーションと、それを使うAPIの変更
- `client/` のUnityアセットと対応する `.meta` ファイル
- 同一機能のUnityコード、シーン、Prefab、Androidネイティブ連携
- API契約の変更と、それに対応するクライアント側の変更
- テストファイル + テスト対象ファイル
- 同一機能（歩数同期、ルーン付与など）の一連の変更

**分離すべきもの:**
- feat vs fix vs refactor vs chore（種類が異なる変更）
- 無関係なドメインの変更
- ドキュメントのみの変更
- 依存関係の更新

**判断基準:** 「このコミットを revert したとき、意味のある単位で元に戻るか？」

### 5. コミット作成

各グループについて順番に：

1. `git add <対象ファイル>` で個別にステージング（`git add .` / `git add -A` 禁止）
2. コミットメッセージを渡す。

```bash
git commit -m "<type>: <日本語の簡潔な説明>"
```

### 6. 完了報告

作成したコミット一覧と、意図的に残した変更を報告する。

## コミットメッセージ

- **type**: feat / fix / refactor / chore / docs / test
- **説明**: 「何が変わるか」を日本語で簡潔に
- 既存の規約がなければscope括弧なし。リポジトリに明示された規約があればそちらを優先する
- PR番号なし（PRマージ時に付与）

例:
- `feat: 歩数同期機能を追加`
- `fix: ルーンが重複して付与される問題を修正`
- `refactor: 歩数取得と同期処理の責務を分離`

## 禁止事項

- `git add -i` / `git rebase -i` など対話的コマンド
- `--amend`（失敗時は新規コミット）
- `--no-verify`（フック省略禁止）
- 依頼外の変更の編集、復元、ステージ
