# 運動量とルーン変換のDB計画

[計画索引](README.md) / [運動データとルーン換算](../features/exercise-rewards.md) / [ルーン経済](../features/economy.md)

## 目的

Health Connectから取得した歩数をサーバーへ保存し、1日の途中でゲームを起動した場合も、前回の変換後に増えた歩数だけをルーンへ変換する。
キャラクター、装備、探索進行は今回の対象に含めず、ルーンをユーザー単位の資源として保存する。
起動時には前回からの差分をポップアップで示し、明示的な取得操作でも同じ差分処理を実行する。
画面にはサーバーに保存された直近7日分の歩数、変換済み歩数、付与ルーンを表示する。

## 今回確定したルール

- 歩数は1歩につき1ルーンへ変換する。
- 1日のルーン獲得上限は設けない。
- 日付は健康データに含まれる端末の `zone` ごとに扱う。
- Health Connectの歩数が後から減っても、付与済みのルーンは取り消さない。
- 初回の報酬取得では、サーバーに保存された過去7日分を対象にする。
- 報酬取得はゲーム起動時に自動で行い、画面上の明示操作でも再実行できる。
- ゲーム起動後のリアルタイム監視や定期ポーリングは行わない。
- 同じ歩数を何度取得しても、ルーンを二重に付与しない。
- 未リリース期間は旧データとの互換性を維持せず、DB全消去後に現行スキーマを適用できればよい。

距離・運動時間などの追加指標は、歩数の実装後に同じ仕組みへ追加できるよう、変換進捗に指標種別と単位を持たせる。
追加指標の換算率、端数、異なる記録の重複処理は別途決める。

## 画面の動作

### 起動時の自動取得

Google認証とHealth Connectの読み取り許可がすでに利用できる場合、起動時に直近7日分の歩数を同期してから報酬請求を行う。
認証・許可が未完了の場合はOS画面を自動表示せず、既存の接続操作を案内する。
ゲーム起動後のリアルタイム監視と定期ポーリングは行わない。

同期完了後は結果ポップアップを開く。ポップアップには今回の獲得合計、日付ごとの追加ルーン、処理後の残高を表示する。
差分が0の場合も「今回の追加はありません」と表示し、直近7日一覧を更新する。

### 明示的な取得操作

画面に「ルーンを取得」ボタンを置く。
ボタン押下時は、現在のHealth Connectの値を読み直し、7日分をサーバーへ同期してから同じ報酬請求APIを呼び出す。
処理中はボタンを無効化し、完了後に差分ポップアップを開く。
差分が0の場合も、明示操作の結果として「今回の追加はありません」とポップアップへ表示する。

### 直近7日分の表示

メイン画面または専用の履歴モーダルに、直近7日分を日付の新しい順で表示する。
各行には日付、歩数、変換済み歩数、当日に付与したルーンを表示する。
未取得、0歩、取得失敗を別の状態として表示する。
画面を開いたまま歩数が増えても自動更新せず、「ルーンを取得」ボタンの完了後に一覧を更新する。

既存のJSON詳細モーダルとは用途を分け、ルーン差分ポップアップと7日一覧は運動報酬専用の表示部品として管理する。

## DBの責務

既存の健康データ層は取得元の事実を保存し、報酬層はその事実をどこまでルーンへ変換したかを保存する。

### 既存の健康データ層

以下のテーブルは変更せず、歩数の取得と同期に利用する。

- `app_users`
- `app_sessions`
- `health_sources`
- `health_days`

`health_days` の `steps` は取得時点の累計値であり、ルーン変換済みの値ではない。

### 日別の変換チェックポイント

新しい `exercise_reward_days` テーブルを追加する。

| 列 | 役割 |
|---|---|
| `id` | 変換対象の識別子 |
| `user_id` | ルーンを受け取るユーザー |
| `source_id` | 歩数の取得元 |
| `day` | 端末タイムゾーンでの日付 |
| `zone` | 日付の基準となるIANAタイムゾーン |
| `activity_type` | 初期値は全体歩数を示す値 |
| `metric_type` | 初期値は `steps` |
| `observed_value` | 最新に確認した運動量 |
| `credited_through_value` | ルーンへ変換済みの累計運動量 |
| `credited_runes` | この日・指標で付与した累計ルーン |
| `rule_version` | 変換ルールの版 |
| `updated_at` | チェックポイント更新日時 |

初期の歩数では `credited_through_value` を累計歩数として使う。
歩数が減少してもこの値を戻さないため、過去に付与したルーンを取り消さず、将来の増加分だけを付与できる。

同じ取得元、日付、タイムゾーン、運動種別、指標種別の組み合わせは一つのチェックポイントにする。
複数の端末や取得元を合算する仕様はまだ決めず、初期実装では別々の取得元を自動合算しない。

### ルーン台帳と残高

`rune_wallets` にユーザー単位の現在残高を保存し、`rune_ledger` に増減の履歴を追記する。

`rune_ledger` には、ユーザー、増減量、理由、対象の日別チェックポイント、変換前後の運動量、ルール版、作成日時を保存する。
リクエスト識別子は `rune_claims` に保存して一意制約を付け、台帳の請求へ紐付けることで通信の再送による二重付与を防ぐ。

報酬付与では、チェックポイント更新、台帳追加、残高更新を一つの確定単位で処理する。
同じ日への同時要求が競合した場合は、サーバー側のチェックポイントを基準に再計算し、差分を一度だけ付与する。

## APIの計画

既存の健康データ同期APIは維持する。

- `POST /health/syncs`
- `PUT /health/sources/:sourceId/days`
- `GET /health/sources/:sourceId/days`

報酬層には次のAPIを追加する。

- `POST /exercise/rewards/claim`：取得元の直近7日分を対象に未変換分を付与する。
- `GET /exercise/rewards/days`：取得元の直近7日分と、日別の変換状態を返す。
- `GET /runes/balance`：ユーザーの現在残高を返す。

歩数は報酬APIの入力として受け取らず、認証済みユーザーが所有する `health_days` からサーバーが取得する。
ゲーム起動時の自動処理と明示操作は、同じ冪等な報酬APIを呼び出す。
ゲームを起動したまま歩数が増えても、リアルタイム監視や定期ポーリングでは取得しない。

`POST /exercise/rewards/claim` の要求には `sourceId` と `requestId` を含め、歩数・ルーン量は含めない。
応答には今回の合計差分、処理後の残高、直近7日分の日別結果を含める。
同じ `requestId` の再送は同じ結果を返し、別の要求でも変換済みチェックポイントを超える付与は行わない。

概念上の応答は次の形とする。

```json
{
  "grantedRunes": 1200,
  "balance": 4200,
  "days": [
    {
      "day": "2026-09-21",
      "zone": "Asia/Tokyo",
      "hasValue": true,
      "steps": 1200,
      "creditedThroughSteps": 1200,
      "runesGranted": 1200,
      "deltaRunes": 1200
    }
  ]
}
```

このJSONはAPI契約を固定するコード例ではなく、入力検証とレスポンス型を設計するための形を示す。

## 実装手順

1. この計画と関連仕様へ確定した歩数報酬ルールを記録する。
2. Drizzleのスキーマへ変換チェックポイント、ルーン台帳、残高を追加する。
3. 新しいD1マイグレーションを生成し、既存の `0000_initial.sql` は変更しない。
4. 過去7日分の `health_days` を初回請求へ利用するサービスとrepositoryを実装する。
5. `POST /exercise/rewards/claim` と取得APIを実装する。
6. 既存のローカル表示経路とサーバー同期経路を一つのCoordinatorへ統合し、Google認証・Health Connect取得・サーバーセッションを二重に開始しない。
7. クライアントAPI契約、起動時請求、明示請求、7日一覧のモデルとPresenterを追加する。
8. 差分ポップアップ、取得ボタン、直近7日一覧を既存Health画面のuGUIへ追加する。
9. DBマイグレーション、API、同時要求、再送、日付境界、歩数減少をサーバーシナリオで検証する。
10. クライアントの起動時処理、ポップアップ、取得ボタン、7日一覧、認証・権限エラーをEditModeとPlayModeで検証する。
11. `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm test:ci`、`pnpm db:check` と、Unityの指定テストを実行する。

## クライアントの配置案

既存のHealth画面を利用し、サーバー報酬の責務だけを追加する。

| 配置 | 役割 |
|---|---|
| `Features/Health/Runtime/Sync/HealthApiClient.cs` | 報酬請求と7日取得のHTTP要求を追加する |
| `Features/Health/Runtime/Sync/HealthSyncContracts.cs` | 報酬結果、日別報酬、残高の型を追加する |
| `Features/Health/Runtime/Sync/HealthClient.cs` または専用Coordinator | 同期後の請求、明示取得、セッション、重複操作を管理する |
| `Features/Health/Runtime/Presentation/HealthScreenPresenter.cs` | 起動時請求と明示請求の状態、差分結果、7日データを画面へ渡す |
| `Features/Health/Runtime/Presentation/` の専用クラス | 差分ポップアップ、7日一覧、閉じる操作、選択復元を管理する |
| `App/Runtime/HealthScreenBootstrap.cs` | Coordinatorと画面部品を一度だけ組み立てる |
| `Features/Health/UI/` | 取得ボタン、差分ポップアップ、7日一覧のPrefab部品を置く |

既存の `HealthJsonDetails` のモーダル管理をそのまま共有基盤へ抽出せず、健康データのJSON表示とルーン報酬表示の状態を分ける。
共通化が必要になった場合だけ、画面全体のモーダル操作へ切り出す。

## 受入条件

- 1,000歩を同期すると1,000ルーンを受け取れる。
- 2,000歩へ増えた後に再取得すると、追加で1,000ルーンだけを受け取れる。
- ゲーム起動時と明示操作を連続して実行しても二重付与されない。
- 初回請求で保存済みの過去7日分を日付ごとに請求できる。
- 起動時の請求結果が差分あり・なしのどちらでも、結果ポップアップが一度だけ表示される。
- 明示的な取得操作では、差分が0でも処理結果をポップアップで確認できる。
- 直近7日分の歩数、変換済み歩数、当日付与ルーンを画面から確認できる。
- 表示中に歩数が増えてもリアルタイム更新せず、次回の起動または取得操作後に更新される。
- 未取得と0歩を区別する。
- 歩数が減少しても付与済みルーンを減らさない。
- 他ユーザーの取得元や日別データを請求できない。
- タイムゾーンが異なる日付を同一日の報酬として扱わない。
- 台帳、日別チェックポイント、残高の更新が途中で分離しない。

## 確認待ち

- 一人のユーザーが複数の端末・取得元を持つ場合の統合方法
- 保存した過去7日分を、ユーザーがいつまで請求できるか
- Health Connectに保存された歩数が削除・再取得された場合の履歴表示
- ルーンの所持上限、消費、失効、有償・無償区分

## 現在の状態

サーバー側は実装済みである。

未リリースのため、旧スキーマからのデータ移行、旧APIとの互換処理、既存DBのバックフィルは実装しない。
検証DBや開発DBに不整合があれば、DBを削除して現行マイグレーションを適用し直す。

- `exercise_reward_days`、`rune_wallets`、`rune_claims`、`rune_ledger` を追加した。
- `0001_exercise_rewards.sql` を生成した。
- `POST /v1/exercise/rewards/claim`、`GET /v1/exercise/rewards/days`、`GET /v1/runes/balance` を追加した。
- 同じ `requestId` の再送、歩数の増分、歩数減少時の取り消しなし、直近7日をシナリオテストで確認した。

クライアント側は、既存のGoogle認証とHealth Connect取得をPresenterから一度だけ利用し、設定されたサーバーURLがある場合に同じ7日分を同期して請求する。
起動時の取得結果と明示操作の結果をポップアップへ表示し、直近7日分の変換済み歩数、日別ルーン、残高を履歴で確認できる。

残っている確認事項は、Unity Editorのライセンスが利用できる環境での再コンパイル、実端末のGoogle認証・Health Connect権限、公開サーバーとの接続である。
