# 縦画面と機種差に対応するUIの実装計画

状態：完了（実装・文書・Editor検証・APK検査済み。Android実機確認は未実施）
作成日：2026-09-13
更新日：2026-09-13

スマートフォンで縦画面を基本とし、画面の大きさや安全領域が変わっても、現在の「1週間の歩数」画面の文章を読めて、すべての操作に到達できるようにする。
既存のuGUI画面を修正し、確定した判断基準を新規の `doc/rules/ui-design.md` にまとめる。
以下は実装に先立って決めた方針であり、実施結果は末尾に記録する。

## 現在の実装と変更理由

対象はUnity 6000.6.0f1のAndroidクライアントとする。
着手時の設定とコードには次の状態がある。

| 対象 | 現在の状態 | 今回の対応 |
|---|---|---|
| [Player設定](../../client/ProjectSettings/ProjectSettings.asset) | 自動回転で4方向を許可 | 通常の縦向きを指定する |
| [画面の生成処理](../../client/Assets/Baryonyx/Features/Health/Editor/HealthScreenAssets.cs) | CanvasScalerは800×1100、Scale With Screen Size、Expand | 拡縮の基準を維持し、文字と操作領域の寸法を見直す |
| [画面の表示処理](../../client/Assets/Baryonyx/Features/Health/Runtime/Presentation/HealthScreenView.cs) | 毎フレームSafeAreaのアンカーとパネル幅を書き換える | 初期表示と表示条件が変わったときに更新する |
| メイン画面 | 一覧だけがスクロールし、説明・状態表示・ボタンは高さが固定 | 内容全体を縦スクロールし、文章に応じて高さを確保する |
| JSON詳細 | 整形済みJSONを折り返さず、上下・左右へスクロール | この操作を維持し、閉じるボタンを安全領域内に置く |
| [既存の画面テスト](../../client/Assets/Baryonyx/Features/Health/Tests/PlayMode/Presentation/HealthScreenScenarioTests.cs) | 認証、接続、一覧、モーダル、JSONスクロールを検査 | 画面サイズ変更と小さい表示領域での操作を追加する |

現状のボタン高は50〜88基準単位で、端末上の48dpを保証する値ではない。
本文にも固定高があるため、折り返し設定だけでは長文を表示しきれない。
実際の表示崩れは実装時にSimulatorで確認し、修正前の画像も残す。

## 「1週間の歩数」のスマートフォン向け改修

[Main](../../client/Assets/Baryonyx/App/Scenes/Main.unity) から起動する既存の「1週間の歩数」を、今回のUIルールを適用する画面とする。
画面の向きを指定する作業と併せて、認証・接続操作、日別一覧、JSON詳細の配置を改修する。
既存の緑系の配色、日本語フォント、等幅のJSON表示を引き継ぎ、次の順序で縦一列に配置する。

| 上からの順序 | 表示内容 | スマートフォン向けの変更 |
|---|---|---|
| 1. 見出し | 「1週間の歩数」と短い説明 | 小さいブランド表記を補足にし、画面の目的を先に読めるようにする |
| 2. 接続状態と操作 | 現在の段階、状態説明、認証・接続・再試行 | 横一列の3段階説明を現在の状態の表示へ変更し、主要ボタンを横幅いっぱいに配置する |
| 3. 対象期間と更新 | 当日を含む直近7暦日の期間、「更新」ボタン | 期間とボタンを別の行へ配置し、日付の折り返しやボタンの圧縮を避ける |
| 4. 日別一覧 | 新しい日付から7日分の日付・曜日・歩数 | 1日分の行全体をタップできるようにし、日付と歩数を別部品で配置する |
| 5. 注記とアカウント操作 | 今日の集計範囲、タイムゾーン、保持方法、「サインアウト」 | 注記を折り返し、サインアウトを一覧・更新と離れた末尾に配置する |

メイン画面は全体を一つのScrollRectでスクロールする。
7日分を一画面に収めるために文字やボタンを縮小せず、初期表示では現在の状態と次に行う操作を読み取れるようにする。
取得後は接続状態を短く表示し、対象期間と一覧の先頭を確認しやすくする。
初期表示でどこまで見えるかは、小さい縦画面の修正前後の画像で確認する。

### 状態ごとの操作

操作の可否は [HealthScreenPresenter](../../client/Assets/Baryonyx/Features/Health/Runtime/Presentation/HealthScreenPresenter.cs) の既存状態に従い、表示の優先順位を次のようにする。

| 状態 | 優先する表示と操作 |
|---|---|
| 未認証 | 「Googleで認証」を表示し、認証後にHealth Connectへ接続することを説明する |
| 認証済み・接続前 | 「Google認証済み」と「Health Connectに接続」を表示する |
| 認証・接続・取得中 | 実行中の内容を表示し、既存の多重実行防止に従って操作を無効化する |
| 取得済み | 接続状態を短く表示し、期間の下に「更新」、続けて7日分の一覧を表示する |
| 権限拒否・利用不可・更新が必要 | 理由を折り返して表示し、既存の条件に従って再接続とHealth Connect設定へのボタンを表示する |
| 取得失敗 | エラー文を省略せずに表示し、Presenterが許可する更新または再接続へ進めるようにする |

認証後は認証ボタンを状態表示へ置き換え、サインアウトは認証済みの場合だけ末尾に表示する。
ボタンを表示する条件と押せる条件は区別し、処理中や詳細表示中は既存の操作制限を保つ。
状態の切り替えで内容の高さが変わる場合は、操作結果を示す状態説明や一覧の先頭を必要に応じて表示範囲へ入れる。
サイズ変更や詳細の開閉では、ユーザーの閲覧位置を維持する。

### 日別の行とJSON詳細

現在の `DayLabels` は、日付・曜日・歩数・矢印を空白でつないだ一つの文字列である。
改修後は日付・曜日、歩数または「データなし」、詳細への矢印を別の表示部品にし、Layout Groupで揃える。
狭い幅や長い数値では行の高さを増やして表示し、値を省略したり自動縮小したりしない。
クリック領域は行全体に設定し、文字や矢印が入力を遮らないようにする。

JSON詳細は、安全領域内に大きく表示するモーダルとする。
上部に対象日、中央に上下左右へスクロールするJSON、下部に「閉じる」を配置する。
背景の一覧はスクロールもクリックも受け付けず、閉じる操作またはAndroidの戻る操作で元の日付と位置へ戻る。

日付順、当日を含む直近7暦日という集計範囲、「0歩」と「データなし」の区別は維持する。
認証と権限の操作順、通常の背面移行・サインアウト時の消去も [既存の機能仕様](../features/health-data.md#ローカル表示画面) に従う。
表示の再配置による再取得や永続化は追加せず、週合計・グラフ・目標歩数などの新機能は今回の範囲に含めない。

## 画面方向と対応範囲

`Default Orientation` を `Portrait` にし、自動回転の許可値も通常の縦向きだけに揃える。
設定はUnityのPlayerSettings APIから変更し、読み戻して保存を確認する。
実行中に繰り返し `Screen.orientation` を設定する処理は追加しない。
この向きの設定はAndroidとiOSで共有されるが、今回のビルド・実機検証は既存のAndroid経路を対象とする。[UnityのPlayer設定](https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsAndroid.html)

タブレットの縦画面は、本文に最大幅を設けて中央に配置する。
OSが横向きやウィンドウサイズ変更を適用した場合も、一列の内容をスクロールして操作できるようにする。
複数列のタブレット専用画面は今回の範囲に含めない。

現在の対象APIは36で、Player設定の `AndroidIsGame` は有効である。
Android 16では大画面で向きの制限が上書きされる場合があり、ゲーム区分などの例外もあるため、生成APKのManifestと端末上の挙動を確認する。
ゲーム区分の変更やOS制限の回避設定は追加せず、縦固定だけに依存しない配置で対応する。[Androidの画面方向とサイズ変更](https://developer.android.com/develop/adaptive-apps/guides/app-orientation-aspect-ratio-resizability)

## レイアウトと表示条件への追従

画面全体の背景とモーダルの暗幕はCanvas全域に描画する。
メイン画面の文字・ボタン、および詳細パネルは、ノッチやシステム領域を避けた **SafeArea** 内に配置する。
SafeAreaは `Screen.safeArea` を画面の幅・高さで正規化してアンカーへ反映し、端末名ごとの分岐は設けない。

レイアウトの更新は、Health機能内に追加する `Runtime/HealthScreenLayout.cs`（予定）へまとめる。
画面幅・高さ、SafeArea、Canvasの論理サイズを比較し、初期表示、再有効化、表示条件の変更時にアンカーとパネル幅を更新する。
毎フレームの比較は許容し、値が同じ場合はRectTransformを書き換えない。
CanvasScalerの更新が反映されたタイミングで適用し、幅・高さが0の間は計算を保留する。
親サイズの変更を次の更新で取りこぼさず、レイアウト更新を再帰させないことをテストする。

メインパネルの最大幅860、詳細パネルの最大幅980を初期値として維持し、それぞれSafeAreaの幅から左右余白を引いた範囲に収める。
実際に割り当てる幅は0未満にならないようにする。
表示条件が変わっても、取得済みデータや開いている詳細を消さず、現在のスクロール位置を表示可能な範囲に保つ。
ここで扱うのは同じ実行中の画面サイズ変更であり、OSによるプロセス終了からの状態復元は対象外とする。

`HealthScreenView` は入力と表示内容を担当し、認証・Health Connect接続・取得処理は既存のPresenterに維持する。
今回の利用箇所はHealth画面だけなので、新しいレイアウト処理も機能内に置く。

## スクロールと文字・操作領域

メイン画面は、見出し、認証・接続操作、状態説明、7日分の一覧、注記を一つの縦スクロール内に置く。
現在の一覧専用ScrollRectは内容のコンテナーに変更し、同じ方向のスクロールを入れ子にしない。
Contentの高さはVerticalLayoutGroupとContentSizeFitterで決め、親による高さ指定との競合を避ける。
主要ボタンは縦に並べて必要な幅と高さを確保し、文章が折り返された場合は行の高さも増やす。

通常の説明、状態、注記は折り返して必要な高さを確保する。
TextMeshProの自動縮小で長文を押し込まない。
JSONは構造とインデントを読むための例外として、等幅フォント・折り返しなし・上下左右のスクロールを維持する。
詳細パネルではJSON本文が伸縮し、見出しと閉じるボタンを固定して表示する。
モーダル表示中の背面操作禁止、戻る操作、閉じた後の選択・スクロール位置の復帰も維持する。

CanvasScalerの基準は800×1100、Expandを継続する。
この値は設計上の座標であり、端末の物理解像度を固定する設定として扱わない。[CanvasScalerの仕様](https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/script-CanvasScaler.html)

スマートフォンの検証下限を表示領域の幅320dpとし、縦画面での初期寸法は次の値から調整する。
dpはAndroidの論理密度に基づく単位で、Unityの基準単位とは区別する。

| 用途 | Unityの基準単位による初期値 | 幅320dpで幅基準の拡縮が働く場合の換算 |
|---|---|---|
| クリック領域の最小幅・最小高 | 120 | 48dp |
| 本文の文字サイズ | 40 | 16dp相当 |
| 補足の文字サイズ | 35 | 14dp相当 |
| 見出しの文字サイズ | 60 | 24dp相当 |
| ページの左右余白 | 40 | 16dp |
| 操作領域間の余白 | 20以上 | 8dp以上 |

これらは今回の初期値であり、縦横比によるExpandの拡縮や実機の表示設定も含めて検証する。
文字サイズの換算はOSのspやシステム文字拡大への対応を意味しない。
操作領域は実際の描画サイズと端末の論理密度から確認し、`Screen.dpi` をそのまま論理密度と見なさない。
Androidでは48×48dp以上のタップ領域と8dp以上の間隔を目安とする。[Androidのタップ領域](https://support.google.com/accessibility/android/answer/7101858?hl=ja)

## 機種差の検証

Editor内の自動テストとDevice Simulatorの画面確認を組み合わせる。
Simulatorでは機種プリセットを選び、次の解像度例に近い条件に加えて、ノッチや上下の安全領域を確認する。
解像度の検査とdpでの操作領域の検査は分けて記録する。

| 表示条件 | 解像度例（幅×高さ、px） | 主に確認すること |
|---|---|---|
| 小さい縦画面、9:16 | 720×1280 | 説明やボタンを含め、画面末尾までスクロールして操作できる |
| 縦長、9:19.5 | 1080×2340 | 余白と一覧の配置、ノッチとの重なり |
| 縦長、9:20 | 1080×2400 | 詳細パネルと下端の閉じる操作 |
| タブレット縦、3:4 | 1536×2048 | 最大幅と中央配置 |
| 横向きの表示領域、4:3 | 2048×1536 | 高さの不足時にも内容と閉じる操作へ到達できる |

追加で幅320dpの表示条件を用意し、操作領域と文字の初期寸法を検査する。
縦横比の切り替え、同じ解像度でのSafeArea変更、詳細表示中のサイズ変更も含める。
画面状態は未認証、取得中、取得前の空表示、7日分表示、7日すべてデータなし、0歩、権限拒否、長い説明・エラー文、長いJSONを対象とする。
検証にはテスト用データを使い、個人の健康データや認証情報を画像へ含めない。

自動テストでは次を確認する。

- 座標計算：上下左右が非対称なSafeArea、パネルの最大幅、余白、0サイズからの復帰。
- 実Prefabの配置：SafeAreaを適用した領域内にスクロールのViewportと詳細パネルが収まり、本文の高さとContentのスクロール範囲が一致する。
- 仮想入力による操作：メイン画面をスクロールして最終日を選択でき、長いJSONをスクロールし、閉じると元の位置へ戻れる。
- 表示中の更新：サイズ変更後もデータと詳細表示が維持され、更新後のRectTransformでクリックできる。
- 歩数の表示：日付と歩数の対応、新しい日付からの順序、「0歩」と「データなし」の区別、長い数値の表示を確認する。
- 状態別の操作：認証から接続・更新へ進めること、末尾までスクロールしてサインアウトできること、再配置だけではProviderの呼び出し回数が増えないことを確認する。

ScrollRect内の要素は一時的にViewport外へ出るため、全要素の常時表示を合格条件にしない。
クリッピングとスクロールによって読み取り・操作に到達できることを検査する。
既存の認証・接続・モーダルのテストも実行し、画面構造を変えた結果、操作を飛ばすテストへ置き換えない。

テストは既存の `Baryonyx.EditModeTests` と `Baryonyx.PlayModeTests` に所属させ、[Unityテスト手順](../rules/client-testing.md)に沿って実行する。
CIでは既存のテスト収集を使い、0件を成功と扱わない。
初回は画像差分用のCI基盤を追加せず、画面・フォント・レイアウト変更時に同じ条件でSimulator確認を行う。

画面変更後はUnity CLIでPlayModeのGameビューを `capture_game_view --source screen` により撮影し、`client/Assets/DevCaptures/` に保存して画像を開く。
Simulatorは配置と基本操作の確認に使い、実機の押しやすさやOS画面からの復帰はAndroid端末で確認する。[Device Simulatorの用途と制限](https://docs.unity3d.com/6000.6/Documentation/Manual/device-simulator-introduction.html)
既存のAndroidビルド手順でAPKを生成し、スマートフォンの回転、システムバー、認証・権限画面からの復帰を確認する。
実機を利用できない項目は、Editorでの成功と分けて未確認として記録する。

## UIルール文書への反映

`doc/rules/ui-design.md` は実装と同時に新規作成する。
画面方向、SafeArea、拡縮と最大幅、スクロール、通常文の折り返し、操作領域、状態表示、機種差の確認時期・受入条件を管理する。
色や余白のトークンを全機能へ配る共通基盤は追加しない。
今回の「1週間の歩数」の配置、状態別の操作、基準寸法とJSONの例外は、健康データ仕様に反映してUIルールからたどれるようにする。
入力欄のキーボード回避やOSの文字拡大など、現在の画面で実装・検証しない項目は、将来の画面で必要になる条件として区別する。

共通ルールの詳細はUIルール文書に集約し、機能仕様とテスト手順からはリンクする。
実装後は計画の状態と検証結果を更新し、実装完了と実機確認の完了を分けて記録する。

## 実施順と受入条件

1. 現在の差分、Unity接続先、実行状態を確認し、代表条件で修正前の画面を記録する。
2. 縦画面の設定と、表示条件に追従するレイアウト処理を追加する。
3. 「1週間の歩数」の状態別の操作、日別の行、スクロール構造と寸法を生成元から修正し、Prefabを再生成する。
4. 再コンパイルとConsoleを確認し、寸法・操作・既存シナリオのテストを実行する。
5. Simulatorの各条件を撮影して確認し、Androidビルドと利用可能な実機で検証する。
6. UIルールと関連文書を反映し、差分・リンク・検証結果を確認する。

完了時には、スマートフォンで通常の縦向きになること、小さい画面とSafeAreaありの画面で文章を読めてすべての操作へ到達できること、詳細の開閉とスクロール復帰が維持されることを確認する。
「1週間の歩数」では、認証、接続、更新、最終日の選択、JSONの閲覧、一覧への復帰、サインアウトまでを幅320dp相当の条件でも操作できることを受入条件とする。
代表条件の画像、実行したテストの件数と結果、実機確認の有無を報告し、未検証の機種やOSまで対応済みと扱わない。

画面全体の縦スクロール、状態別のボタン表示、日付と歩数の個別表示、長文で高さが増える配置、詳細表示中の背面スクロール停止を実装した。

### Androidビルド

既存の `AndroidBuild.Build()` でARM64・IL2CPPの開発用APKを `client/Builds/Android/baryonyx.apk` に生成した（111,691,635 bytes）。
ビルド結果は `Succeeded` で、APKの署名検査と健康データ連携の組み込み検査が成功した。
Manifestではパッケージ名 `com.croissantlab.baryonyx`、最小SDK 26、対象SDK 36、`UnityPlayerGameActivity` の `screenOrientation=1`（Portrait）を確認した。
歩数の読み取り権限を含み、書き込み・バックグラウンド・履歴拡張の権限を含まないことも確認した。

BuildReportのエラー集計1件は、ビルド中にUnity CLIの応答が5秒でタイムアウトしたログであり、コンパイルやAPK生成の失敗ではなかった。
ビルド処理は継続して成功し、最終BuildReportと生成APKで結果を確認した。
警告8件はPipelineの実行時設定、診断用シンボル、TMPシェーダーの非推奨指定、IL2CPPによる大きなメソッドの出力分割に関するものだった。
ビルド結果は `client/Logs/portrait-build-result.json`、Manifestの読み取り結果は `client/Logs/portrait-apk-manifest.txt` に保存した。

### 実機で残る確認

接続済みのAndroid端末は0台だった。
幅320dp相当の配置は論理密度2倍を仮定した640px幅で検査しており、実機の密度や物理的なタップ領域は測定していない。
端末回転、システムバー、タップのしやすさ、Google認証・権限画面からの復帰は実機確認を残す。
iOSのビルド・実機確認、OSの文字拡大、ソフトウェアキーボードの回避は今回の対象外である。
