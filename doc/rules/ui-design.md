# UnityのUI設計ルール

[設計・開発ルールの索引](README.md)

アプリは横画面に固定し、表示領域の大きさが変わっても文章を読めて必要な操作へ到達できるようにする。
ゲーム画面の主役（キャラ、メニュー、リスト、パネル）は中央の16:9 Core Areaへ収め、操作とHUDはSafe Areaの端へ固定する（[画面端の部品と中央の層の部品](#画面端の部品と中央の層の部品)）。
uGUIで作るゲームの画面（Top・Home・案内人の画面・冒険・戦闘）に適用する。
削除した「1週間の歩数」と[操作試作](../archive/game-wireframe.md)の構成と寸法は、[削除した歩数画面の記録](../archive/health-data-local-screen.md#スマートフォン向けの画面構成)と試作の記録に残す。

## 画面方向と拡縮

アプリの向きはPlayer設定の `Auto Rotation` とし、自動回転を許す向きは `Landscape Left` と `Landscape Right` だけにする。
Androidの `Auto Rotation Behavior` は `Sensor` とし、端末の自動回転がオフでも、横画面のまま傾きに合わせて左右を反転させる（マニフェストの `screenOrientation` は `sensorLandscape`）。
向きはPlayer設定だけで決め、起動時や画面ごとの処理から `Screen.orientation` や自動回転の許可値を設定しない。
AndroidとiOSで共有される設定であるため、検証したOSの範囲は機能仕様に明記する。[UnityのPlayer設定](https://docs.unity3d.com/6000.6/Documentation/Manual/class-PlayerSettingsAndroid.html)

CanvasScalerの `Scale With Screen Size` を使い、基準解像度を設計上の座標として扱う。
ゲーム画面の基準解像度は1920×1080とし、CanvasScalerは高さを基準に拡縮する。
基準解像度を端末の物理解像度や対応端末の制限と見なさない。
アンカーとLayout Groupで利用可能な幅に追従し、本文には最大幅を設けて大きい画面で中央に配置する。[CanvasScalerの仕様](https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/script-CanvasScaler.html)

背景画像は元の縦横比を保ったまま表示領域を覆い、親のRectTransformからはみ出す部分を切り取る。
この処理は共有の [`ResponsiveBackground`](../../client/Assets/Baryonyx/Shared/UI/ResponsiveLayout/ResponsiveBackground.cs) が担当し、画像の縦横比に合わせて表示矩形を計算する。
CoreAreaの外側へ広がった横幅は背景や環境演出へ使い、必須UIやゲーム本体の座標を横幅に合わせて引き伸ばさない。

画面端へ固定するUIはSafe Area配下のアンカーへ置く。
画面全体を覆う背景と暗幕はSafe Areaの外側に置き、文字、ボタン、閉じる操作は [`SafeAreaFollower`](../../client/Assets/Baryonyx/Shared/UI/ResponsiveLayout/SafeAreaFollower.cs) または既存のSafe Areaレイアウト配下に置く。
ボタンは固定座標ではなく、四隅・辺・中央のアンカーと設計座標のマージンで配置する。
CoreArea内のゲーム本体とSafe Area配下の操作UIは、同じ親で伸縮させない。
画面が16:9より狭いときは、中央の層を [`WorldLayerFit`](../../client/Assets/Baryonyx/Shared/UI/ResponsiveLayout/WorldLayerFit.cs) で縮め、隅のボタンの下へキャラを潜らせない。
Layout Groupが子のサイズを決める範囲では、子のアンカーと `sizeDelta` を手動で設定しない。

OSから横向きやサイズ変更を適用された場合も、内容をスクロールして操作できるようにする。
Androidの大画面では向きの指定が上書きされる条件とゲーム区分などの例外があるため、生成APKのManifestと実機で確認する。
横向きの指定だけを表示崩れへの対策としない。[Androidの画面方向とサイズ変更](https://developer.android.com/develop/adaptive-apps/guides/app-orientation-aspect-ratio-resizability)

### 画面端の部品と中央の層の部品

画面の部品は、16:9から幅が変わったときの動き方で、**画面端の部品**と**中央の層の部品**に分ける。
画面端の部品はSafe Areaの端に付いて動き、中央の層の部品は画面の中央に留まる。
横長の画面で余った幅には、背景だけを見せる。

| 種類 | 対象 | 置き方 | 16:9より横長の画面 | 16:9より狭い画面 |
|---|---|---|---|---|
| 画面端の部品 | 位置を覚えて押す操作と、常に出す情報（HUD）。戻る、閉じる、パンくず、所持数、設定、ホームの行き先のボタンと歩数の板、冒険のメニューと凡例、戦闘の行動順・エネルギー・山札・ターン終了・手札など | Safe Area配下に置き、四隅・辺のアンカーと設計座標のマージンで位置を決める | Safe Areaの端へ寄る | 端に付いたまま、大きさを保つ |
| 中央の層の部品 | 画面の主役。キャラ、案内人の画面の案内人とメニュー、リスト、項目のパネル、ダイアログの窓など | 中央の1920×1080の層に置き、層の中の設計座標で位置を決める | 中央に留まる | 層ごと縮む（[`WorldLayerFit`](../../client/Assets/Baryonyx/Shared/UI/ResponsiveLayout/WorldLayerFit.cs)） |

どちらか迷う部品は、横長の画面で端へ離れたときに、主役とのつながりが切れるかで決める。
案内人とその横のメニューのように、並びで意味をなす部品は同じ中央の層に置く。
ホームの歩数の板は、主役と並べずに単独で読む情報のため、画面端の部品とする。

中央の層は、縮んでも付けておきたい辺を軸にして縮める。
案内人の画面の生成処理（[GuideMenuAssets](../../client/Assets/Baryonyx/Shared/UI/GuideMenu/Editor/GuideMenuAssets.cs)・[GuidePanelLayout](../../client/Assets/Baryonyx/Shared/UI/GuideMenu/Editor/GuidePanelLayout.cs)）では、案内人とメニューの層（`Core`）は案内人の腰を付けたままにする下端を、項目のパネルの層は上の帯の下端を軸にする。

## 現行のUI構成

Unity `6000.6.0f1` のゲーム内UIは、uGUI、TextMeshPro、Input Systemを使う。
画面、ボタン、数値などゲーム内のTextMeshProテキストはKiwi Maruで統一する。
例外として、戦闘中に浮かぶダメージと回復の数字にはDela Gothic Oneを使う（[戦闘の数字のフォント](../../client/Assets/Baryonyx/Features/Combat/UI/Fonts/README.md)）。
フォント本体、TMPアセット、ライセンスの参照先は[ゲーム画面のフォント](../../client/Assets/Baryonyx/Shared/UI/Fonts/README.md)に揃える。
新規画面もuGUIを既定とし、UI Toolkitは独立した新規画面で明確な利点があり、入力・描画順・フォーカス・ライフサイクル・テストの境界を設計できる場合だけ採用する。
uGUIとUI Toolkitを同じ画面で使う場合は、採用理由とEventSystem、Input System UI Input Moduleの構成を記録する。
IMGUIはゲーム中のUIに使わず、エディター専用の診断・制作ツールに限定する。

uGUIではCanvas、Prefab、Layout、Animator、Presenterの責務を分ける。
頻繁に変わるHUDと静的な背景を同じCanvasへ詰め込まず、既存の画面・Presenter・EventSystem・PlayModeテストとの境界を保つ。

## 安全領域とレイアウトの更新

文字やボタンは、ノッチやシステム領域を避ける **SafeArea** 内に配置する。
背景とモーダルの暗幕は画面全体へ描画し、モーダルの操作部品はSafeAreaに収める。
SafeAreaは `Screen.safeArea` と画面サイズから求め、機種名ごとの固定値は使わない。

初期表示、再有効化、画面サイズ・SafeArea・Canvasの論理サイズの変更時に配置を更新する。
値を毎フレーム比較してもよいが、変化がないときはRectTransformを書き換えない。
サイズが0の間は計算を保留し、有効なサイズへ戻ったときに再適用する。
親のレイアウト更新を取りこぼしたり、変更通知から再帰的に更新したりしない。

画面サイズの変更だけで取得済みデータを再取得・消去せず、詳細表示と閲覧位置を保つ。
背景へ移ったときのデータ消去など、機能固有のライフサイクルは機能仕様に従う。

## 背景を主役にした視覚階層

ゲーム画面は背景とプレイ中の状態を主役にし、セクションを太い枠や不透明なカードで常時分割しない。
情報のまとまりは、位置、余白、整列、見出しと本文の大きさ、明暗差の順に組み立てる。
それだけで読み取りにくい場合だけ、薄い灰色の面、細い区切り線、局所的なグラデーション、透過した暗い操作面を加える。
選択状態や重要な操作など、誤読を防ぐ必要があるまとまりには枠や不透明な面を使う。

探索・戦闘のHUDは背景へ重ね、文字やアイコンの背後に局所的な暗幕やグラデーションを置く。
編成・装備・報酬・設定などの全画面操作は、背景を見せる黒の透過レイヤーを基本にする。
本文や比較値が多い画面は透明度だけで可読性を保たず、ぼかし、暗い操作面、十分なコントラストを組み合わせる。

枠や板が要るときは、どの画面でも次の2つの共通部品だけを使い、画面ごとに枠・板の形や画像を作らない。

| 部品 | 使う場所 | 生成 |
|---|---|---|
| [枠つきの表示](../features/screens/guide.md#枠つきの表示) | 画面いっぱいの面（左右とも透ける面・金の2本線・見出し・タブ）と、その上に重ねる窓（レベルアップ・確認のダイアログ） | [GuideFrameAssets](../../client/Assets/Baryonyx/Shared/UI/GuideMenu/Editor/GuideFrameAssets.cs) |
| [すりガラスのカード](../features/screens/guide.md#すりガラスのカード) | 押す・選ぶもの、押せない箱、景色の上の札・帯・ボタン | [GlassCardAssets](../../client/Assets/Baryonyx/Shared/UI/GlassCard/Editor/GlassCardAssets.cs) |

景色の上に直に置くカードは、板を濃い紺（`GlassCardAssets.SceneFillColor`）にして読みやすくする。文字の背後の、四方へ薄くなる暗い下地（`FeatherPlate`）や暗幕は枠ではないため、この2つに含めない。

全画面モーダルは確認や獲得など一つの作業に集中させ、背面のクリックとスクロールを止める。
編成のパーティ・装備・育成のように複数の操作を続ける画面は、見た目が同じ透過基調でも全画面スクリーンとして扱い、戻る操作と再入場時の状態を画面仕様へ記す。
透明度に依存した表示は背景の明るさで読みにくくなるため、高コントラスト表示や透明度を下げる設定を妨げない。

[Appleのマテリアル指針](https://developer.apple.com/jp/design/human-interface-guidelines/materials)と[Material 3のダイアログ指針](https://m3.material.io/components/dialogs/overview)を、透過レイヤーと全画面モーダルの設計根拠として参照する。

## スクロールと文章

小さい画面では、内容の高さを増やしてスクロールさせる。
同じ方向のScrollRectを入れ子にせず、操作するスクロール領域を一つに定める。
Viewportで内容をクリップし、Contentの高さを文章と子要素から求める。
親のLayout Groupと子のContentSizeFitterが同じ寸法を競合して決めないようにする。

通常の説明、エラー、注記は折り返して表示し、TextMeshProの自動縮小で固定高へ押し込まない。
日付、数値、矢印などを揃えるときは別の表示部品を使い、空白の数で位置を調整しない。
数値は読める大きさを保ち、長い場合は表示行の高さを増やす。
JSONのようにインデントを読む必要がある表示は、機能仕様で折り返しと横スクロールの例外を定める。

## 操作領域と状態表示

Androidのタップ領域は48×48dp以上、操作領域間の間隔は8dp以上を目安とする。
小さいアイコンでも、クリック領域は周囲を含めて確保する。[Androidのタップ領域](https://support.google.com/accessibility/android/answer/7101858?hl=ja)

dpとUnityの基準単位を区別し、実際の描画サイズと検証端末の論理密度で確認する。
`Screen.dpi` は論理密度としてそのまま利用しない。
文字の設計上の大きさを、OSのspやシステム文字拡大への対応済みという意味で記載しない。

現在の状態と次に行える操作を近くに表示し、主要なボタンは狭い画面でも読める幅にする。
処理中は内容を表示して多重実行を防ぎ、失敗時には理由と再試行の操作を示す。
操作の表示条件と有効条件は分けて管理し、認証・権限・取得の可否は機能の状態に従う。
サインアウトなど閲覧を終える操作は、更新や一覧選択と離して配置する。

モーダル表示中は背面のクリックとスクロールを止める。
閉じる操作を表示範囲内に保ち、戻る操作でも閉じられるようにする。
閉じた後は元の選択と閲覧位置へ戻す。
操作結果を表示するためのスクロールと、単なる画面サイズ変更に伴う位置の保持は区別する。

## 読み込みの待ち時間を見せない

画面を開くときや操作したときのシーン・サーバーの読み込みは、「読み込み中…」の文字で待たせる前に、待ち時間そのものが見えない形を次の順に検討する。
上の段で足りるなら、下の段を使わない。

| 順 | 形 | 使える場面 | 例 |
|---|---|---|---|
| 1 | 待たずに結果を出す（楽観的更新） | 次の操作がサーバーの結果を必要としない | 装備・編成の変更、世界地図のマスの支払い（[サーバーに置くときの作り方](data-storage.md#サーバーに置くときの作り方)） |
| 2 | 前に読んだ内容をすぐ出し、裏で読み直す | アプリを動かしている間に一度読んだ画面 | 編成・装備・ライブラリ・商会の「買う」（同上） |
| 3 | 互いに依存しない読み込みを同時に送る | 1つの画面が複数を読む | 育成・装備・ライブラリ・ホームのACT（同上） |
| 4 | もともとある演出の間に読む・保存する | 結果が要る操作に、歩く・喜ぶなどの演出が付いている | マスの移動、勝利の演出の間の保存、全滅の帯の間の読み直し（[冒険の画面](../features/screens/adventure.md#冒険の画面)） |
| 5 | 幕を閉じたまま読み、描き終えてから開く | 初めて開く画面で、読む前の姿や描く途中が見えてしまう | 世界地図（[世界地図を開く画面](../features/stage-progression.md#世界地図を開く画面)）、探索（[冒険の画面](../features/screens/adventure.md#冒険の画面)） |
| 6 | 見える所をカードの裏で埋め、読み終えたらめくる | 一覧を初めて読む間 | 編成・商会・ライブラリの一覧（[カードの裏面](../features/screens/guide.md#カードの裏面)） |
| 7 | 「読み込み中…」の文字 | 上のどれも使えない、または幕で覆う上限を超えた | 商会の「売る」「合成」、帯の形の一覧 |

どの形でも、次を守る。

- 読む前の既定値・仮データ・初期の位置を、一瞬でも見せない。開いた直後に別の姿へ飛ぶ・現れる動きは、不具合として直す。
- 幕を閉じたまま待つときは、覆う時間の上限を決め、超えたら開いて「読み込み中…」を出す（世界地図は3秒）。読めなかったときは、知らせを見せるために開く。覆ったまま別のシーンへ移るときは、開いてから閉じ直さない。
- シーン間の幕は短い暗転にし、長い演出はTopからHomeへの移動だけに使う（[画面遷移の演出](../features/screens/top-home.md#画面遷移の演出)）。演出の時間を延ばして読み込みを隠さない。
- 待ちを隠す形を変えたら、デバッグルームの「通信」（[デバッグルームの一覧](../features/screens/top-home.md#デバッグルームの一覧)）で、ふつう・遅い（1秒）・とても遅い（3秒）・失敗のそれぞれを、初めて開いたときと開き直したときで確かめる。

## 停止中の表示の切り替え

同じシーンの中で、Play中の操作によって表示するUIが切り替わる画面は、停止中のUnity Editorでも切り替えた見た目を確かめられるようにする。
対象は、項目のパネル、一覧と個別のページ、重ねた画面、ダイアログ、結果や報酬の表示など、押すと出るUIである。
停止中は Awake・Start・OnEnable が動かないため、切り替えの処理を持たないと、Prefabに作り込んだUIも最初の表示しか見えないからである。

| 項目 | 規則 |
|---|---|
| 表示の中身 | 切り替えて見せるUIは、生成時に仮データでPrefabやシーンへ作り込む。停止中に通信・保存・静的な状態から読まない |
| 画面の部品 | 表示を切り替える部品に [`IEditModePreview`](../../client/Assets/Baryonyx/Shared/UI/EditModePreview/IEditModePreview.cs) を付け、状態の名前の一覧（`PreviewStates`）と、その状態にする処理（`ShowPreviewState`）を書く。処理はPlay中と同じ表示の切り替え（`Render` など）を呼び、自分のGameObjectの下だけを変える |
| Inspector | 部品の型ごとに、空の [`EditModePreviewEditor`](../../client/Assets/Baryonyx/Shared/UI/EditModePreview/Editor/EditModePreviewEditor.cs) の派生を、機能の `Editor/` に置く。Inspectorの上に「停止中の表示の切り替え」と状態ごとのボタンが出る |
| 入れ子 | 閉じたパネルの中の画面は、パネルを開く画面の状態の一覧に「パネル名 › 状態」として含め、親のInspectorから切り替える |
| 保存しない | 切り替えは、元のUIを隠し、保存しない複製（名前の末尾が「(停止中の表示)」）の上で行う（[`EditModePreviewer`](../../client/Assets/Baryonyx/Shared/UI/EditModePreview/Editor/EditModePreviewer.cs)）。シーンやPrefabの保存、シーンを閉じる操作、Play Modeの前に自動で元の表示へ戻し、Undoに記録せず、変更済みにもしない |

新しく画面を作るとき、また既存の画面に切り替わるUIを足すときは、同じ変更で状態の一覧へ加え、停止中に各ボタンで切り替わることと、元の表示へ戻ることを確かめる。
動きを伴う演出（数が増える、粒子が流れるなど）は、止めた1コマを見せるだけでよく、動きはPlay Modeで確かめる。

## 操作を求めない通知

「〇〇をセットしました」「設定（準備中）」「獲得ルーンはありません」のように、プレイヤーに操作を求めない通知は、どの画面でも共通の**通知の帯**で出す。
通知の帯は、戦闘画面の技名と同じ見た目の部品であり、画面ごとに別の見た目のトーストを作らない。

| 項目 | 規則 |
|---|---|
| 見た目 | 暗い半透明の帯（色 `#05060A`、不透明度0.88）に白い文字（44px）。帯の幅は文の長さに合わせ、最小520px（設計座標） |
| 位置 | 画面の上の中央。帯の中心を上端から104pxに置き、戻るボタンと画面の題名のあいだに出す。画面の中身の上には重ねない |
| 表示時間 | 1.4秒表示して0.3秒で消える。表示中に次の通知を出すと、文を差し替えて数え直す |
| 入力 | タップを受けず、背面の操作を止めない |

実装は [NoticeBand](../../client/Assets/Baryonyx/Shared/UI/Toast/NoticeBand.cs) とし、画面の生成処理から [NoticeBandAssets.Build](../../client/Assets/Baryonyx/Shared/UI/Toast/Editor/NoticeBandAssets.cs) で置く。
選択や確認が必要な知らせ（取り消せない操作の確認、通信の失敗からの再試行など）は、通知の帯ではなく、閉じる操作を持つダイアログで出す。

## 機種差を確認する条件

画面の追加、レイアウト・フォント・長文表示の変更時に、同じ条件で検査する。
横画面アプリの検証条件として、少なくとも次の表示領域を確認する。

| 条件 | 確認する内容 |
|---|---|
| 横16:9（1920×1080） | 16:9のCore Areaへ必須UIが収まること |
| 横19.5:9（2340×1080） | 中央の層の部品が中央に留まり、画面端の部品がSafe Areaの端にあること |
| 横20:9（2400×1080） | 中央の層の部品が中央に留まり、画面端の部品がSafe Areaの端にあること |
| 横4:3 | Core Areaを保ち、内容と閉じる操作へ到達できること |
| ノッチあり、非対称のSafeArea | 文字やボタンとOS領域が重ならないこと |
| 表示中のサイズ・SafeArea変更 | データ、詳細表示、操作、閲覧位置を保てること |

各条件で、取得前の空表示、取得中、データあり・なし、0の値、権限拒否、長い説明・エラー文、詳細画面を確認する。
スクロールする内容の全要素が常に見えることは求めず、正しくクリップされ、スクロールで読み取り・操作に到達できることを検査する。

自動テストは座標計算、実Prefabの配置、仮想入力からの操作を検査し、[Unityのテスト手順](client-testing.md)で実行する。
GameビューとDevice Simulatorは配置と基本操作の目視確認に使う。
Simulatorは実機の動作すべてを再現しないため、文字の読みやすさ、タップ、システムバー、OS画面からの復帰は [Androidの実機確認](client-android-testing.md#手動で残す確認) で確かめる。[Device Simulatorの用途と制限](https://docs.unity3d.com/6000.6/Documentation/Manual/device-simulator-introduction.html)
実機確認に使うmoto edge 50 pro（1220×2712、20:9）は、Unity Editorの起動時に [GameViewDeviceSizes](../../client/Assets/Baryonyx/Editor/GameViewDeviceSizes.cs) がGameビューのAndroidグループへ横向きの `moto edge 50 pro (2712x1220)` として登録する。[端末仕様](https://en-us.support.motorola.com/app/answers/detail/a_id/178982/~/specifications---motorola-edge-50-pro)
この登録は画面サイズだけを再現し、Safe Areaとパンチホールは含まない。

確認画像は `client/Assets/DevCaptures/`（Git対象外）に保存し、機種・解像度・状態・テストデータの使用有無を記録する。
個人の健康データや認証情報を画像へ含めない。
実機を利用できない項目と未検証のOSは、Editorの成功とは分けて報告する。

入力欄を追加するときはキーボードによる遮蔽、システム文字拡大へ対応するときはOS設定への追従を、対応する機能の受入条件に含める。
現在の画面に入力欄やシステム文字拡大の連携は実装していない。
