# コードと文書の読み方

[設計・開発ルールの索引](README.md)

調べものでは、読む前に当たりを絞り、必要な範囲だけを1回読む。
人もAIも同じ規則に従う。
2026-09-21週から10-19週にかけて、1件の作業の道具の呼び出しは中央値109回から192回に増えた。
増えた分の最大は読み込みで、読んだファイルの種類は変わらないまま、読みの45〜55%が同じファイルの読み直しだった。

## 当たりを絞ってから読む

- 文字列を探すときは、まず `grep -rl`（ファイル名だけ）で対象のファイルを絞る。`--include='*.cs'` などで種類を、`-m <件数>` で1ファイルあたりの件数を限る。中身は、絞ったファイルの該当の行の前後だけを読む。
- `client/Assets/Baryonyx` のような広いフォルダーへの再帰grepで、出力を丸ごと読まない。件数が多いときは、条件を足して絞り直す。
- 大きいファイル（目安として500行や30KBを超えるもの）は、行の範囲を指定して読む（`sed -n '120,200p'`、読み取りの道具の範囲指定）。行番号は、grepの `-n` で先に調べる。
- `doc/` の文書は、[見出しの索引](../heading-index.md)で文書と節の行番号を調べてから、その節だけを読む（[見出しの索引の使い方](documentation-policy.md#見出しの索引)）。

## 読み直さない

- 1回読んだ範囲は、その作業の中で読み直さない。必要な事実は、読んだときに控えておく。
- 自分で書き換えたファイルは、書き換えの結果を確かめるためだけに読み直さない。読み直すのは、ほかの作業が同じファイルを変えた知らせがあったときと、書き換えが失敗したときだけにする。

## ログと差分

- `client/Logs/Editor.log` やテストのログは、末尾（`tail -n 50`）か、`grep` で必要な行（`error CS`、`Exception`、テスト名）だけを読む。ログを丸ごと読まない。
- Unityのテストとコンパイルは、[テストの実行](client-testing.md#実行と結果確認)のスクリプトを使う。このスクリプトは、成功なら要約だけを、失敗なら失敗したテストとコンパイルエラーの行だけを出す。
- `git diff` は、まず `git diff --stat` で変わったファイルと行数を見る。中身は、必要なファイルだけを `git diff -- <パス>` で読む。

## 待つ

- テスト、ビルド、Editorが空くのを待つ処理は、1回の呼び出しの中でループさせ、長いものはバックグラウンドで流して完了の通知を待つ。状態の確認（`editor_status` や `echo` など）を、何十回も別々に呼ばない。

## 広い調べもの

- 多くのファイルにまたがる調べもの（命名の違う箇所の洗い出し、関係する画面の一覧など）は、サブエージェントに任せ、結論だけを受け取る。
- 任せるときは、調べる範囲と、すでに分かっていることを渡す。
