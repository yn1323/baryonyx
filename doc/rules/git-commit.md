# commitの分け方とメッセージ

[設計・開発ルールの索引](README.md) / [commitの手順](../../AGENTS.md#commitの手順)

commitする変更の選び方・分け方・メッセージの書き方と、ほかの作業と並行しているときの控え方を定める。
commit前のテストの全件実行と、失敗したとき・実行できないときの扱いは、ルートの AGENTS.md の[commitの手順](../../AGENTS.md#commitの手順)を正本とする。
ユーザーが名前で呼ぶ手動の [commit](../../.agents/skills/commit/SKILL.md) スキルも、この文書に従って進める。

## 対象の選び方

今回の依頼に属する変更だけをcommitする。
ユーザーや並行作業の変更は残し、編集・復元・ステージしない。

次の変更はcommitに含めない。
変更に含まれていても、内容を変えたり戻したりしない。

- `.env*`・認証情報・秘密値のファイル
- Unityの `Library/`・`Temp/`・`Logs/` などの生成物と、ビルドの成果物

追跡しているアセットの `.meta` は、対応するアセットと一緒に含める。
APKのビルドが書き換えたファイルはcommitせず、[ローカルビルドと配布処理の検証](client-android-testing.md#ローカルビルドと配布処理の検証)に従って戻す。
依頼外のファイルがステージ済みでも、indexの状態を変えない。
今回のcommitから安全に外せないときは、対象と理由を報告して止める。

## 分け方

1つのcommitは、revertしたときに意味のある単位で元に戻るまとまりにする。

同じcommitにするもの：

- `server/` のDB定義・マイグレーションと、それを使うAPIの変更
- `client/` のUnityアセットと、対応する `.meta`
- 同じ機能のUnityのコード・シーン・Prefab・Androidのネイティブ連携
- APIの契約の変更と、それに対応するクライアントの変更
- テストと、テストの対象
- 同じ機能（歩数の同期、ルーンの付与など）の一連の変更

分けるもの：

- 種類の違う変更（下のtypeが違うもの）
- 関係のない機能の変更
- 文書だけの変更
- 依存関係の更新
- フォントアセットに書き足された文字の差分（[client/AGENTS.md](../../client/AGENTS.md#フォントアセットの差分)に従い、別の `chore` のcommitにする）

## ステージの仕方

`git add <対象のファイル>` で1つずつステージし、`git add .`・`git add -A` は使わない。
1つのファイルに複数の作業の変更が混ざるときは、`git diff <パス>` をhunkごとに切って `git apply --cached` に渡す。
2回目からは、hunkを番号ではなく中身の文字列で選ぶ。1回ステージすると残りのhunkの番号がずれ、別の作業のhunkが入るためである。

## メッセージ

`git commit -m "<type>: <説明>"` の形で書く。

- typeは `feat`・`fix`・`perf`・`refactor`・`chore`・`docs`・`test` から選ぶ。
- 説明は、何が変わるかを日本語で簡潔に書く。
- PR番号は付けない（PRをマージするときに付く）。

今の履歴には、scopeを付けた `feat(workshop): …` の形と、付けない `feat: …` の形が混ざっている。
2026-10-05からはscope付きが多く、scopeには変えた機能の名前（`workshop`・`world-map`・`battle`・`skills` など）を使っている。
どちらにもそろえず、scopeを付けるかはcommitごとに選んでよい（2026-11-02、ユーザーの判断）。

例：

- `feat: 歩数同期機能を追加`
- `fix(adventure): ダンジョンの幕を、マスと道を描き終えてから開く`
- `perf(health): 歩数のパネルを押したときの保存とルーンの請求を1回の要求にまとめる`

## 使わない操作

- 対話的なコマンド（`git add -i`・`git rebase -i` など）
- `--amend`（失敗したら新しいcommitにする）
- `--no-verify`（フックを飛ばさない）

## 並行作業中のcommit

ほかのチャットや作業が同じ作業ツリーを編集している間にcommitするときは、テストした内容とcommitする内容をそろえるため、変更を控えてから進める。

1. commitの前に、変更したファイルの更新時刻と、ほかの作業の動き（[Editorの札](client-testing.md#複数のチャットで1台のeditorを使うとき)の持ち主など）を確かめる。編集中の作業があれば、待つか今の状態でcommitするかをユーザーに聞く。
2. 一時のindexに今の内容を控える。`GIT_INDEX_FILE=<一時ファイル> git read-tree HEAD` のあと、同じ `GIT_INDEX_FILE` で対象のパスを `git add` する。
3. 控えた内容で、[commitの手順](../../AGENTS.md#commitの手順)の全件のテストを実行する。文書検査は、控えを `git checkout-index -a --prefix=<一時フォルダー>/` で書き出し、そこで実行する。編集途中の文書が検査に落ちるときは、そのファイルを控えから外す。
4. 1つのファイルに複数の作業が混ざるときは、HEADに一方の変更だけを足した版を作り、`git hash-object -w` で控えに入れる。
5. 控えたindexの項目を `git update-index --index-info` で本当のindexへ移してからcommitする。作業ツリーを読まないため、テストのあとのほかの作業の編集は混ざらない。
6. 最後に、控えとcommitした内容に差がないことを確かめる。
