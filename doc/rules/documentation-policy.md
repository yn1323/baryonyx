# 文書管理方針

## 配置と役割

文書はリポジトリ直下の `doc/` に置き、[文書一覧](../README.md)からたどれるようにする。
入口のファイル名は `README.md` に統一する。

| 場所 | 所有する内容 |
|---|---|
| ルートの `AGENTS.md` | 常時適用する作業上の制約と参照先 |
| `doc/architecture.md` | システム全体の構成と責務の境界 |
| `doc/game/` | ゲーム全体の企画、世界、用語、MVP、初期入力 |
| `doc/features/` | 機能ごとの要求、動作、制約、実装の入口 |
| `doc/catalog/` | 安定したIDを持つ個別データと記入テンプレート |
| `doc/art/` | 共通の画風、画像化の手順、外見・性格の比較索引 |
| `doc/settings/` | 設定の用途・正本・変更手順への索引 |
| `doc/tools/` | 文書のリンク・ID・生成索引の検査 |
| `doc/qa/` | ユーザーから想定される質問と回答、症状別の対処法 |
| `doc/rules/` | 継続して使う設計・開発上の判断基準 |
| `doc/plans/` | 変更ごとの提案、判断理由、実装手順、受入条件 |
| `.agents/skills/` | 特定作業の発動条件と手順 |

一つの規則は一つの文書で管理し、他の文書からはリンクする。
配色やテスト層などの詳細ルールは、対応する `doc/rules/` の文書に置く。

## 機能とAPI

一つの機能に関わるクライアントとバックエンドの仕様を、一つの機能文書からたどれるようにする。
画面のないサーバー処理も `doc/features/` で扱う。

機能文書には、目的、主な動作、制約、実装状況、関連コードの入口を記す。
APIの入力・出力など、コードから生成できる詳細は生成元へ集約し、手書きの一覧と二重管理しない。
独立したAPI資料が必要になったら `doc/api/` を追加する。

## ユーザー向けQA

ユーザーから想定される質問と回答は `doc/qa/` に置き、[QA一覧](../qa/README.md)からたどれるようにする。
回答には、ユーザーが確認・操作する手順と、解決しない場合の次の確認先を記す。
機能仕様の詳細は対応する `doc/features/` へリンクし、端末や外部サービスの条件には公式資料と確認日を添える。
実例を記す場合は、利用者の報告と、こちらで確認した事実・未確認事項を区別し、個人情報を含めない。

## 現行仕様と計画

現在の実装を確認するときは、コードと設定を確かめる。
期待する要件と実装に差があれば、その差を明記し、要件を暗黙に実装へ合わせない。
未実装の案は、実装済みの機能として記載しない。

計画には「提案」「進行中」「完了」「見送り」の状態を記す。
計画を完了するときは、確定した動作と設計判断を機能文書や設計ルールへ反映する。
実装完了と実環境への反映完了を区別する。
廃止・置換した資料を保存する必要が生じたら `doc/archive/` を設け、理由と後継文書を記録する。

## 更新時の確認

- 機能の動作を変更したら、対応する機能文書と実装状況を更新する。
- 文書を追加・移動したら、入口と被参照元のリンクを更新する。
- 記載したコードのパスやコマンドが、現在のリポジトリと一致するか確認する。
- 存在しない予定パスは、今後の配置案であることを明示する。
- 日本語の文章規範は [japanese-tech-writing](../../.agents/skills/japanese-tech-writing/SKILL.md) を参照する。

## 仕様追加時の矛盾の扱い

仕様の追加依頼を受けたら、既存の正本と追加内容を照合する。
既存仕様と矛盾する内容がある場合も、矛盾のない部分の追加を先に進め、その追加と文書検査を終えてからユーザーに質問する。

1. 追加内容を、既存仕様と両立する部分、明示された変更・旧案の置き換え、判断が必要な矛盾に分ける。
2. 矛盾のない部分を対応する仕様へ追加し、関連文書・索引・リンクを更新して検査する。ユーザーが今回明示した廃止・置き換えは、その指示を根拠に反映し、同じ判断を再確認しない。
3. 未解決の矛盾は、既存の記述と参照先、今回の内容、両立しない条件、影響範囲を正本の「確認待ち」などへ記録する。既存仕様を推測で上書きせず、相反する案を両方とも確定仕様として並べない。
4. 追加済みの内容を報告したうえで、矛盾箇所についてどちらを採用するか、または条件を分けるかをユーザーに質問して確認する。質問には対立する内容と文書へのリンクを添える。
5. 回答後に該当箇所と関連文書を更新し、「変更と判断の記録」へ日付・根拠・影響先を残す。確認待ちのまま実装や別の仕様へ波及させない。

未決事項の具体化、異なる対象へのルール、企画と現行実装の差は、確定仕様同士の矛盾と区別する。
適用範囲の違いで両立する場合は、その範囲を明記する。
新しい依頼だからという理由だけで、明示されていない既存ルールの廃止を決めない。

## 索引と読み込み範囲

全体索引 → 分野索引 → 対象文書の順に読む。
個別データは分類のREADMEから対象へ進み、画像案の比較では比較索引から直接対象へ進む。
索引には所在と短い説明を置き、数値・計算式・長い仕様や手動の実装進捗一覧を複製しない。

追加した文書は、必ず対応する索引からリンクする。
分類別の個別データ一覧と画像対象の比較索引は、個別MDのメタデータから生成する。
その他の索引は手書きの所在案内とし、文書の追加・移動時に同時更新する。

## MDの形式と状態

新しい企画仕様・個別定義・参照資料には、先頭に次の形式のメタデータを付ける。
README・AGENTSと既存の機能・ルール・計画・QAは、必要な改訂時に移行する。

```yaml
---
id: feature-example
type: specification
status: 未決
updated: 2026-09-13
---
```

この例の日付は形式例であり、コピー時は実際に内容を更新・確認した日へ変更する。
メタデータは1行1項目の単純な文字列とし、配列・入れ子・複数行・空値・行末コメントは使わない。
UTF-8・LFで保存し、リンクは相対パス、見出しは具体的な項目名にする。

| 項目 | 規則 |
|---|---|
| id | 小文字英数字とハイフン。文書全体で一意。名称が変わっても原則維持し、廃止したIDを別対象へ再利用しない |
| type | specification、reference、source、definition、visual-entity、templateのいずれか |
| status | 未決、候補、一部確定、確定、見送り、記録、運用中、テンプレートのいずれか |
| updated | 内容を更新・確認した日。閲覧しただけで日付を進めない |
| name・category | 個別データで必須。分類は配置フォルダー名と一致させる |

「未決」は判断がない状態、「候補」は案がある状態、「一部確定」は合意済みと未決が混在する状態とする。
文書全体の状態だけで各項目の確度を推測せず、本文を「確定している方針／確定した設定」「候補」「未決事項」に分ける。
初期企画で挙げた数値例や課金候補を、既定値や採用済み機能へ変えない。
未決・未確認・対象外を区別し、対象外には理由を記す。

個別データはIDと同じファイル名にし、分類内に1対象1ファイルで置く。
他の対象は名称だけで参照せず、IDと相対リンクで参照する。
対象ごとの状態と画像制作の状態は別にし、画像の生成成功だけで採用済みとしない。

## 正本と変更の記録

企画の要求・判断は対応する仕様を正本とする。
コード・ツールが読む設定・APIスキーマ・DB定義は実行上の正本とし、要求との相違は仕様へ明記する。
矛盾があっても、片方を根拠なく上書きして一致させない。

ゲームマスタの実行形式は未決である。
採用時は、MDから生成するのか、別のマスタから文書を生成するのかを決める。
数値をコードとMDの両方で手編集する運用は作らない。
設定索引には用途・所在・既定値の確認先・変更手順を記し、秘密値や外部管理画面の実値は複製しない。

通常の差分はGitで追う。
仕様の採否、制約、数値の意味を変えた場合は、その正本の「変更と判断の記録」に日付・理由・根拠・影響先を短く追記する。
初期入力は履歴として保存し、後から決まった内容を過去の合意として書き換えない。
見送った個別案も状態と理由を残し、参照中のIDを説明なく削除しない。

## 変更に合わせた見直し

| 変えたもの | 同じ変更で確認する文書 |
|---|---|
| 運動データ・権限・日付 | 健康データ、運動報酬、目標、日付、QA |
| 資源・倍率・報酬 | 経済、目標、戦闘、探索と進行、報酬テーブル |
| キャラ・装備・スキル・効果 | 個別定義、戦闘計算、装備生成、育成 |
| 外見・性格・採用画像 | 対象の文章、比較用メタデータ、画像記録、生成比較索引 |
| 保存・認証・公開環境 | アカウントとセーブ、全体構成、設定索引、関連手順 |
| コード配置・設定ファイル | 実装入口のリンク、設定索引、関連ルール |
| 機能の実装・公開 | 仕様の実装欄、受入条件、確認結果と未確認事項 |

実装・設定の変更時は、仕様への影響があるかを差分レビューで確認する。
影響がなければ日付だけを更新せず、その理由を作業報告またはPR本文へ記す。
外部サービス・ライセンス・OS条件は、採用・更新・公開の判断時に一次資料を確認し、出典・確認日・未確認範囲を残す。

## 機械検査と限界

[文書検査](../tools/README.md)でリンク先・見出し・ID重複・メタデータ・索引の生成差分・索引からの到達を確認する。
GitHub Actionsにも同じ検査を置き、コード側の移動によるリンク切れも検出する。

検査は文章と実装の意味の一致、外部サービスの現状、画像の類似性までは判定しない。
日付が新しいことやリンクが通ることを、内容が最新である証明として扱わない。
仕様変更時の見直しと、実装・採用画像・実環境の確認を併せて行う。
